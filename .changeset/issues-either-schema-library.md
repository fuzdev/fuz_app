break: `perform_action` and `ActionEvent` read validation issues from either schema library, so an input or output parsed with a `@fuzdev/fuz_schema` schema gets the same answers as a Zod one there. `ActionSpec` still types its schemas as Zod: surface generation, the broadcast API, the RPC test helpers, and the testing generators call Zod-only APIs. `resolve_issues_invalid_reason(input_schema, issues, input)` and `to_invalid_params_error(input, issues, params)` take the value that was parsed as a new third argument, and take a fuz_schema schema and its `SchemaIssue`s beside Zod's; `resolve_invalid_reason` takes a fuz_schema schema too, reading `invalid_reason` from fuz_schema's `meta` (`schema_meta.ts` adds the key to its `SchemaMeta`). For a fuz_schema input the `data.reason` rule is Zod's: the first issue's field's declared reason, none when an issue is on the input itself (a non-object, or an unknown key on the input object, an `unknown_key` issue with a one-key path), and for a strict `object` input none whenever the input has a key the schema doesn't name, even when fuz_schema's hundred-issue cap left that key out of the issues, as the Rust spine refuses unknown keys before reading fields. `safe_parse_dropping_unknown_keys` (`http/schema_helpers.ts`) takes a fuz_schema schema too and returns `{ok: true, value}` or `{ok: false, issues}` in place of Zod's `safeParse` result; it strips unknown keys until a parse succeeds or reports anything else. After the first parse that reports unknown keys, one schema-guided pass deletes every key a strict fuz_schema `object` doesn't name anywhere the schema reaches (entries, array items, record values, the `variant` option), so a payload of many unknown keys costs two parses, not one per hundred keys; a key under a fuz_schema `union` is never stripped (the union fails as one issue of its own), and a later pipe stage is stripped only as reported. It stops after `UNKNOWN_KEY_PASSES_MAX` (4) passes for either library, returning the last failure. A Zod parse reports every unknown key at once, so a Zod payload is stripped in one pass, a pass per narrowing pipe stage. A `ZodError` or a fuz_schema `SchemaError` thrown from the cell hooks `validate_data` and `validate_policy` becomes `invalid_params`. New: `schema_issues.ts` — `parse_any`, `issue_is_on_input`, `unknown_key_targets`, `format_issues`, `is_schema_validation_error`, and the types `ValidationSchema`, `AnyIssue`, `ParseAnyResult`. Nothing on the wire changes for Zod specs. To migrate: pass the parsed value as the third argument to `resolve_issues_invalid_reason` and `to_invalid_params_error`, and read `safe_parse_dropping_unknown_keys`'s result as `result.ok` / `result.value` / `result.issues` for `result.success` / `result.data` / `result.error.issues`.
