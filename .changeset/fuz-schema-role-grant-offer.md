break: the role_grant_offer domain's schemas are `@fuzdev/fuz_schema` schemas, not Zod: the eight actions' inputs and outputs (`auth/role_grant_offer_action_specs.ts`), `RoleGrantOfferJson` (`auth/role_grant_offer_schema.ts`), and the notification params (`auth/role_grant_offer_notifications.ts`, whose specs' `output` is fuz_schema's `s.void`). Every object refuses unknown keys as the `z.strictObject`s did; `role` is the fuz_schema `RoleName` twin, `scope_kind` the new fuz_schema `ScopeKindName` twin (`auth/scope_kind_schema_fuz.ts`, `@nodocs` while the Zod one stays, built from constants `auth/scope_kind_schema.ts` now exports, `SCOPE_KIND_NAME_LENGTH_MESSAGE` and `SCOPE_KIND_NAME_PATTERN_MESSAGE`), `acting` the fuz_schema `ActingActor`; the types, read by `Infer`, keep their names and shapes. Every input gets the Zod schema's verdict and output, the list and history inputs reading an omitted input as a fresh `{}` and history's `offset` held to `Number.MAX_SAFE_INTEGER` as Zod's `.int()` held it, and their surface entries are unchanged as JSON but for an `info` diagnostic on the create and assign inputs, whose `check` pairing `scope_kind` with `scope_id` has no JSON Schema form. Two verdicts change: `RoleGrantOfferJson`'s `scope_kind` is a `ScopeKindName` or `null` (it was any string), so an output or notification carrying an offer row whose `scope_kind` is off the grammar fails under DEV output validation, and its JSON Schema gains the grammar's `maxLength` and `pattern`; and the revoke notification's params gain a required `scope_kind`, the revoked grant's, beside `scope_id` (both `null` for a global grant), which the TS spine sends and a sender that omits it fails. That notification's method is renamed from `role_grant_revoke` to `role_grant_revoked`, past tense like `role_grant_offer_received` / `_accepted` / `_declined` / `_retracted`: it shared its method with the admin RPC action `role_grant_revoke`, which a WS action set can't register twice. The constant, spec, builder and params are renamed with it (`ROLE_GRANT_REVOKED_NOTIFICATION_METHOD`, `role_grant_revoked_notification_spec`, `build_role_grant_revoked_notification`, `RoleGrantRevokedParams`); the action, its audit event type `role_grant_revoke`, and its error reasons keep their names. A client that matched the notification on the old method string matches `role_grant_revoked` instead, and the Rust spine sends the new method in step. Under DEV an invalid input's `-32602` issues keep their `kind`, `path`, `expected` and `received`, each `message` now fuz_schema's text, apart from where one issue stands for Zod's two or more: a half-scoped create or assign input with a field failure gets the fields' issues alone, where Zod added the pairing `check` issue after them; a `role` or `scope_kind` both too long and off the grammar gets the one length issue; and a history `limit` past `Number.MAX_SAFE_INTEGER` gets the `max_value` issue of its bound alone, where Zod's `.int()` put its safe-range `max_value` issue before it. Production answers carry no issues, and the reasons are unchanged. The WS endpoint of an RPC list holding the role_grant_offer actions (`to_ws_actions`) now lists the role_grant_offer notifications after them, as handler-less `remote_notification` methods from the new `role_grant_offer_notification_actions`, `role_grant_revoked` among them; an inbound frame for one is still answered `method_not_found`, and a committed surface snapshot changes by those entries, so regenerate it. Under DEV, `create_role_grant_offer_actions` checks each notification's params against its spec's `input` before sending it (`create_validated_notification_sender`), logging a mismatch and sending it either way; production sends unchecked. `describe_role_grant_offer_notification_ws_tests` takes `scoped_role` and `scope_kind` for a scoped-revoke case, and its revoke frames are held to the new key. Generated `action_collections.ts` types these actions with `Infer<…>`; regenerate with `gro gen`. To migrate: code calling `.parse` / `.safeParse` / `.shape` / `.extend` on these schemas uses fuz_schema's `parse`, `parse_or_throw` and `def` (`@fuzdev/fuz_schema/schema.ts`), `get_schema_entries` (`@fuzdev/fuz_schema/introspect.ts`) for the piped and defaulted inputs, or `parse_any` (`schema_issues.ts`) for either library; a Rust or other sender of the revoke notification sends method `role_grant_revoked` and adds `scope_kind`.
