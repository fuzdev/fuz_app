break: one grammar for the three credential headers on both spines — the session cookie is written raw and read verbatim, so sessions minted before this stop verifying and every user logs in again

- break: the session cookie value is written raw, never percent-encoded, in the Rust spine's exact `Set-Cookie` string — `name=value; Path=/; HttpOnly; Secure; SameSite=Strict; Max-Age=N` — and read back verbatim. A cookie minted by an earlier version is percent-encoded, reads as invalid, and is cleared: one forced re-login on deploy. A session cookie now verifies on either spine, whichever minted it
- break: `SessionOptions.cookie_options`, `SessionCookieOptions` and `session_cookie_options` are removed, with the surface diagnostics that warned of a weakened cookie. The attributes are fixed (`SESSION_COOKIE_ATTRIBUTES`), as on the Rust spine, so `Secure` can't be turned off: a deployment on plain HTTP off localhost can no longer hold a session
- break: the session cookie is read from the request's `Cookie` lines by `read_session_cookie_value` (`auth/credential_headers.ts`), not a framework cookie parser: several lines read as their `; ` join, each pair is stripped of SP and HTAB only, the first pair beginning `<name>=` wins, and its value is taken as sent. A percent-encoded or quoted value, `name = value`, and a valid cookie behind an invalid first pair of the same name no longer authenticate
- break: an empty session cookie value (`name=`) is present and invalid — `parse_session('')` returns `null` and `process_session_cookie('')` answers `'clear'`, where both read it as no cookie. `get_session_cookie` returns `string | null`
- break: `set_session_cookie` throws on a cookie name or value outside RFC 6265 (`is_cookie_name`, `is_cookie_value`), so a `SessionOptions.encode_identity` must emit cookie-octets (a non-string is refused too, so a test keyring whose `sign` returns `undefined` fails; `create_stub_app_deps().keyring.sign` now answers a string); `create_app_server` throws at assembly on a session cookie name that is no cookie-name, and on session options that can't mint: it mints one sample cookie through them, calling `deps.keyring.sign` once, so a keyring test double needs `sign`
- fix: an `Authorization` or `X-Daemon-Token` header sent on two lines is discarded — the request continues without that credential. On a Node WebSocket upgrade a repeated `Authorization` authenticated with its first line, since `@hono/node-server` builds an upgrade's headers from Node's deduplicated view; the credential legs now read the request's raw header lines (`get_header_lines`, `http/header_lines.ts`) where the runtime provides them
- the clearing `Set-Cookie` for an invalid session cookie is the fixed string `format_session_clear_cookie` gives (`format_session_set_cookie` gives the minting one), on every response the context builds and ahead of the route's own cookies
- `auth/daemon_token.ts` adds `DAEMON_TOKEN_REGEX` and `is_daemon_token_shaped`; `read_bearer_token` and `read_daemon_token` (`auth/credential_headers.ts`) are the legs' readers
- DEV only: `X-Fuz-Auth-Debug` reports a discarded bearer or daemon token only when the header read as a well-formed token
- testing: `cross_backend/credential_conformance.json` is the shared table of raw header lines and their reading, run by `describe_credential_conformance_cross_tests` through the new `_testing_credential_read` backdoor (`testing_credential_read.ts`, in `TESTING_BACKDOOR_METHODS`) and by `describe_credential_conformance_wire_cross_tests` over raw sockets. Both are in `SUITE_NAMES`, so `describe_spine_cross_suites` runs them: the first skips itself where the backdoor is undeclared; the second needs `SECRET_FUZ_COOKIE_KEYS` in the config's env (or `cookie_keys` in `overrides`), `account_verify` on the RPC endpoint admitting all three credentials, the login route, and — with `capabilities.ws` — an upgrade that admits each credential with no `Origin`; it takes a `setup` with no `extra_actors`, with `capabilities.ws_account_actions` reads `account_verify` on the socket too, and seeds its own two `extra_accounts` (`CREDENTIAL_SESSION_ACCOUNT_USERNAME` with `CREDENTIAL_SESSION_ACCOUNT_PASSWORD`, `CREDENTIAL_BEARER_ACCOUNT_USERNAME`). `_testing_credential_read` takes at most `TESTING_CREDENTIAL_READ_LINES_MAX` lines of `TESTING_CREDENTIAL_READ_LINE_LENGTH_MAX` characters, and refuses any other `lines` `invalid_params` with `invalid_header_line`. A config declaring the whole `TESTING_BACKDOOR_METHODS` list must mount the new action on its binary
- break: testing: `describe_credential_header_robustness_cross_tests` drops its two duplicated-header cases (`duplicate X-Daemon-Token (valid + conflicting) never escalates → one non-2xx response`, `duplicate Authorization bearer headers (both garbage) do not authenticate → one non-2xx response`), now exact rows of the wire suite, and `CredentialHeaderRobustnessCrossTestOptions.daemon_token` with them
- testing: `transports/ws_raw_client.ts`'s `connect_raw_ws` takes `header_lines` (the upgrade's header lines as written, so a name can repeat) and returns the `handshake` head; `transports/raw_http.ts` adds `raw_http_request` (a request framed from an array of header lines, so a name can repeat) and `raw_http_header_values` (every value of one response header); the fetch transport's jar drops a cookie cleared with `Max-Age` of zero or less, as a browser does
