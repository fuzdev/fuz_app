fix: string length bounds are enforced on `String.length` — UTF-16 code units, the count the Rust spine uses — whatever the installed Zod counts. They were enforced by Zod's `.min()` / `.max()` alone, and a newer Zod within the `^4` peer range counts Unicode code points there, so on it a string of astral-plane characters over a cap in code units was accepted (a 64-unit `kind` cap admitted up to 64 emoji, 128 units) and a `Password` of 6–11 astral characters was refused. Every `.min()` / `.max()`-bounded wire string schema (a bare `.min(1)` aside, which reads the same in either count) is now built by the new `bounded_string({min?, max, max_message?})` in `primitive_schemas.ts`: `Username`, `UsernameProvided`, `Password`, `PasswordProvided`, `RoleName`, `ScopeKindName`, `CellPath`, `CellItemPosition`, the cell `kind` on `cell_create` and `cell_list`, the API token `name`, the grant `scope_kind`, the offer `message`, decline `reason` and revoke `reason`, and the `actor_search` `query`. On a Zod that counts code units nothing changes; on one that counts code points an over-cap astral string is now refused at input validation. On a Zod that counts code points, a stored offer `message` or decline `reason` over its cap in code units, accepted before this fix, now fails `RoleGrantOfferJson`, the offer output and notification schema: the server's output validation logs it (DEV only), and a typed RPC client, which validates every response against its output schema in every mode, refuses the response carrying it. The generated JSON Schema (`minLength` / `maxLength`) is unchanged, and a refusal carries the issues a code-unit Zod reports, whichever Zod is installed
