break: validation issues take one shape on every refusal, whichever schema library refused: `WireIssue` (`schema_issues.ts`), `{kind, path, expected, received, message}`, `@fuzdev/fuz_schema`'s `SchemaIssue` as JSON — the DEV-only REST `issues` of the three schema-failure `ValidationError`s, the DEV-only RPC `data.issues` of `invalid_params` (the dispatcher's and the cell hooks' `validate_data` / `validate_policy`) and of a refused request envelope, and an `ActionEvent`'s `validation_errors`. They were each library's own issue objects. New: `WireIssue` and `to_wire_issues(issues, input)`, which takes either library's issues and the value that was parsed. A fuz_schema issue keeps its fields, its `message` the `format_issue` text (the path included). A Zod issue maps to the kind fuz_schema reports for the same check, with Zod's own message: `invalid_type` to the type's kind (`int` to `integer`, `null` / `undefined` / `void` / `nan` to a `literal`, `nonoptional` to `missing_key`, a type fuz_schema has no kind for to a `check` expecting its name; a missing key is the type expected with `received: 'undefined'`, as fuz_schema reports it), `too_small` / `too_big` to `min_length` / `max_length` for a string, array, set or file and `min_value` / `max_value` otherwise, `invalid_format` to `uuid`, `iso_datetime`, `regex` or else a `check` expecting the format's name, `unrecognized_keys` to one `unknown_key` per key with the key appended to the path, `invalid_union` to a `variant` (with a discriminator) or a `union` expecting each option as fuz_schema names it, `invalid_value` to a `literal` or `one_of`, and `custom`, `not_multiple_of`, `invalid_key` and `invalid_element` to a `check`; `received` is read from the input at the issue's path. `ValidationError.issues` and the fact routes' 400 schema are `Array<WireIssue>`, refusing an issue in either library's own shape. A Zod issue with a `bigint` bound, which `JSON.stringify` refused, now serializes. Production bodies are unchanged, and a server in production does no mapping: the issues it sends are built only under DEV. `dev_only` takes a thunk, `dev_only(() => value)`, called only under DEV. To migrate: read an issue's `kind` for Zod's `code`, and its `message` for the text; `expected` is now fuz_schema's text (`int` is `integer`); expect one `unknown_key` issue per unrecognized key, each with the key on its `path`; the Zod issue's other fields are gone — `keys`, `minimum` / `maximum` / `origin` / `inclusive`, `format` / `pattern`, `values`, `divisor`, a union's `errors`, and the nested `issues` of a key or element; validate DEV error bodies against `WireIssue` (loose, so a field a newer server adds passes); regenerate surface snapshots that embed `ValidationError`'s JSON Schema.
