break: provenance stamps carry no foreign key, and a purge takes an advisory lock in place of every admin's account row

- break: the `fuz_auth` migration `drop_provenance_stamp_foreign_keys`, appended (twinned by name and statements on the Rust spine), drops the foreign keys of `actor.updated_by` / `deleted_by` and `role_grant.granted_by` / `revoked_by` / `source_offer_id`. A stamp keeps the id it was written with after its actor or offer is purged, where `ON DELETE SET NULL` nulled it. A purge's cascade no longer writes other accounts' rows through a stamp, so an admin revoking a grant they granted, or an owner's first edit of their own cell, no longer deadlocks with that account's purge
- break: the migration runs `ALTER TABLE … DROP CONSTRAINT`, which `@fuzdev/pglet-wasm` 0.1.x refuses (`0A000`): a database on pglet-wasm, the default test database among them, needs 0.2.0, the new peer floor
- break: `fuz_cell`'s `full_cell_schema` is rewritten in place (pre-stable): `cell.updated_by` and `cell_grant.granted_by` carry no foreign key, so a cell grant by a purged granter is written rather than failing with `23503`. `cell.created_by` keeps its foreign key. A database that recorded `full_cell_schema` before keeps the two foreign keys — drop and re-bootstrap it, or, for a long-lived one, run by hand: `ALTER TABLE cell DROP CONSTRAINT IF EXISTS cell_updated_by_fkey; ALTER TABLE cell_grant DROP CONSTRAINT IF EXISTS cell_grant_granted_by_fkey;`
- break: `query_account_lock_admins_for_purge` is removed. A purge takes `query_account_purge_advisory_lock` first — `pg_advisory_xact_lock` on `ACCOUNT_PURGE_ADVISORY_LOCK_KEY`, taken only by purges — so two purges whose cascades cross (offers between their accounts, accepted or declined, and invites each claimed) take turns, and a purge no longer locks every admin's account. A consumer calling the removed query (a test playing a purge) takes the advisory lock instead; one that relied on it holding the target's account row also calls `query_account_lock_for_purge`
- fix: a purge and a delete run their keeper and last-admin guards again once they hold the target's row — the purge's `query_account_lock_for_purge`, the delete's `query_account_lock_live`, each taken after the first guard. Whether the target is an admin is read unlocked, and with no row of a non-admin target held before its own, an accept making it an admin could commit while the removal waited, and a revoke it let pass end every other admin — the removal then removed the last admin
