break: the action spec types (`actions/action_spec.ts`) are plain TS interfaces — `ActionSpec`, `RequestResponseActionSpec`, `RemoteNotificationActionSpec`, `LocalCallActionSpec`, and the `ActionSpecUnion` union — not Zod schemas, so there is no `ActionSpec.parse` / `.safeParse` / `.extend`, no `.default()` filling a field, and `ActionSideEffects` is gone (`side_effects` is a `boolean`). A spec's `input` and `output` are typed `ValidationSchema`, a Zod or a `@fuzdev/fuz_schema` schema, where they were `z.ZodType`; a notification's `output` is `z.ZodVoid` or fuz_schema's `s.void`. Specs written with `satisfies` keep compiling: every field the interfaces require was already required on the inferred types. `ActionKind`, `ActionInitiator` and `ActionEventPhase` stay Zod enums, now built from the new const lists `ACTION_KINDS`, `ACTION_INITIATORS` and `ACTION_EVENT_PHASES`, which `is_action_spec` reads. `ValidationOutput` (`schema_issues.ts`) tests for a fuz_schema schema first, and the new `ValidationInput` gives a schema's input type the same way; `HandlerForSpec` (so `rpc_action`) types a handler's input and output by `ValidationOutput`, so a fuz_schema spec's handler is typed by its schemas where it was `unknown`, and the testing `rpc_call_for_spec` types `params` and `result` by `ValidationOutput`. The spec types are no longer runtime exports, so import them with `import type`. To migrate: build a spec as a literal with `satisfies RequestResponseActionSpec` (or the kind's interface) instead of parsing it, spelling `kind`, `auth` and `async`; replace `ActionSideEffects` with `boolean`; and where code reads a spec's schema as Zod — `spec.input.safeParse(x)`, `spec.output.parse(x)`, a `z.ZodType` parameter fed `spec.input` or `spec.output` — use `parse_any(spec.input, x)` (`schema_issues.ts`, `{ok, value}` or `{ok: false, issues}`), or narrow first with `is_zod_schema` / `assert_zod_schema`.
