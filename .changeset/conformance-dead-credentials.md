break: the conformance table pins the session cookie on every row, asserts the JSON-RPC error code, and gains the dead-credential principals

- break: `ConformanceCase.expect.set_cookie` (`SessionCookieEffect`: `'none' | 'clear' | 'set' | 'clear_then_set'`) states what a response does to the session cookie, and **omitted means `'none'`**: every HTTP row now fails on a `Set-Cookie` for the session cookie it doesn't declare. A row on a route that mints or clears (login, signup, bootstrap, logout, password change) states its effect, and so does any `/api` row whose request carries a session cookie that fails verification (`'clear'`, or `'clear_then_set'` on a login). The lines are compared byte for byte with `format_session_set_cookie` / `format_session_clear_cookie` (`cross_backend/session_cookie_effect.ts`: `classify_session_cookie_effect`, `find_session_cookie_mints`, `filter_session_set_cookies`)
- break: a floor beside the fingerprint one: on the HTTP legs no response outside 2xx mints a session cookie (`assert_session_cookie`, exported), and a row expecting a mint on such a status is refused when the table is described
- break: every RPC error row asserts `error.code`, on the HTTP and WS legs: the new `expect.error_code` when the row names one, else the code its status maps to (`http_status_to_jsonrpc_error_code`). A row whose refusal uses another code sharing that status (`invalid_request` at 400) now fails until it states it
- `expect.error_reason: null` requires an RPC error to carry no `data.reason`, where a reason-less denial was pinned by status alone. `check_conformance_cases` (exported, run when the table is described) throws on `error_reason: null` or `error_code` on a REST row, whose error body always names its code
- break: `ConformancePrincipal` gains `tampered_cookie`, `wrong_daemon`, `unknown_bearer`, `revoked_session`, `revoked_token` and `expired_token`, each on a transport carrying only that credential; none is a WebSocket case, and neither is a row whose `set_cookie` isn't `'none'`
- break: `TestFixture` requires `mint_revoked_session`, `mint_revoked_token` and `mint_expired_token` (`default_cross_process_setup` and the in-process setup provide them; a hand-built fixture adds them). Each proves its credential authenticated before killing it (`assert_credential_authenticates`, exported — it needs `account_verify` mounted) and that the revoke removed a row. `mint_expired_token` mints an account of its own, shortens its token to `EXPIRED_TOKEN_SHORTEN_SECONDS` (`query_shorten_credential_expiry`, the statement behind `_testing_shorten_credential_expiry`, which a cross-process backend must mount) and waits `EXPIRED_TOKEN_WAIT_MS`, on both fixtures — one real-time wait per `expired_token` row, in-process too
- break: `ConformanceCaseResponse`, `RpcCallRawResult` and `DifferentialRawResponse` carry `set_cookies`, every `Set-Cookie` line in order; `normalize_differential_response` takes the session cookie's name as a second argument and `DifferentialResponse` gains `session_cookie`, so the differential fails a row where one backend clears or mints and the other doesn't, at the path `session_cookie`
- `mint_test_session` also returns the session's `session_hash`
