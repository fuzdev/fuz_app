  • http/auth_shape.ts

    Canonical auth shape for action specs and route specs.

    Replaces the discriminated 'public' | 'authenticated' | 'keeper' | {role} literal that conflated authentication, account resolution, actor resolution, and authorization into a single value. The flat record names each axis the dispatcher actually walks:

    • account — does the dispatcher require / load / skip the account?
    • actor — does the dispatcher require / load / skip the acting actor?
    • roles — disjunction of permitted roles (any-of); absent = no role check.
    • credential_types — restricts the credential channel (e.g. daemon_token); absent = any authenticated credential.
    • required_scope — the capability an api token's scope must admit to reach this route (surface:<name>); route specs only, absent = no scope gate.

    The same shape governs both ActionSpec.auth (in actions/action_spec.ts) and RouteSpec.auth (in http/route_spec.ts). The canonical schema lives here in http/ because that preserves the existing actions → http dependency direction (and http/error_schemas.ts / http/surface.ts consume the type).

    Every registry-time invariant is enforced at registration, inside the dispatcher loops every spec passes (apply_route_specs for route specs, compile_action_registry for create_rpc_endpoint and register_action_ws): the cross-axis invariants 1, 3, and 4 by assert_route_auth_invariants, which reads the auth shape alone, and invariant 2 (the `actor !== 'none' ⟺ input or query declares acting?: ActingActor` biconditional), which introspects the spec's input/query schemas, by assert_route_auth_acting_biconditional. Specs are plain objects that no registration path parses, so both checks live in code rather than on a schema.

  • http/body_limit.ts

    Request body size limit — rejects an oversized body with 413, and a Content-Length it cannot read with 400, before auth and validation.

    Wraps Hono's bodyLimit with a header-first check:

    • A Content-Length that is not a plain run of ASCII digits (abc, -1, +5, 1e9, 0x1F4, empty, or a combined 5, 500) is refused with 400 {error: 'invalid_content_length'}. A cap cannot be applied to a length that does not parse, and bodyLimit passes such a request on uncounted. The runtimes' HTTP parsers answer their own bodiless 400 to most of these before the application sees them, so this branch is defense in depth where they do and the refusal where they do not: Node's refuses them all; Bun hands over a repeated equal header as one combined value (50, 50) and refuses the rest (observed on Node 24.14.1, Bun 1.4.3). The Rust spine's parser (hyper) refuses a malformed value and differing repeats, and accepts an equal repeat as the one value.
    • A request whose Content-Length exceeds the cap is refused with 413 {error: 'payload_too_large'}, whatever its method. A digit run of any length compares as a number, so one too long to represent exactly is over the cap, never unreadable. Over a socket that branch is reached on Node, whose parser hands over any length below 2^64 and refuses a longer one with its own 400. Bun.serve hands none over: with its default options it answers a length past 128 MiB with its own 413, and one of 2^63 - 1 or more with its own 400 (observed on Node 24.14.1, Bun 1.4.3).
    • Both refusals answer on the header alone — without touching c.req.raw.body — and carry Connection: close.
    • A request with a well-formed Content-Length beside Transfer-Encoding, or with no Content-Length, falls through to bodyLimit, which measures the bytes that arrive: with Transfer-Encoding the declared length does not frame the body. bodyLimit reads the body into memory, up to the cap, before the next middleware runs, so that 413 — sent once more than the cap has been read, with no Connection: close — also comes ahead of the origin check, auth and the handler. The Rust spine counts such a body as its handler reads it instead, so there a refusal made on the headers answers first; which status an over-cap body with no declared length gets when another refusal also applies is implementation-defined across the two (docs/security.md §"Body Size Limiting"). The Node and Bun parsers refuse a request carrying both headers with their own 400; hyper accepts one, drops its Content-Length, frames the body as chunked, and closes the connection after the response.
    • A well-formed Content-Length within the cap is trusted to frame the body, as the runtime's HTTP parser enforces.

    What the connection does after the header 413 is the runtime's (docs/security.md §"Body Size Limiting"):

    • Node (@hono/node-server) closes at once, the body unread. The Connection: close header is what does it: without one the adapter holds the connection for a drain window and then closes or, the body untouched and arriving within the window, reads it off and serves the next request.
    • Bun closes at once, the body unread, honouring the header. Bun 1.4.4 is the tested floor (CI's pin); the close needs 1.4.3 — an older Bun kept the connection after the 413 and served the next request (correctly framed) — so run Bun at the floor or later.

  • http/dev_route_error_check.ts

    The DEV-only error check: an outer middleware that logs every JSON error response its route doesn't declare.

    Mounted outermost by create_app_server, so it sees what every layer answers — a middleware's refusal (the body limit, the origin check, the auth guards) as much as a handler's or the error catch's. After the request it finds the route the request reached (create_route_lookup: Hono's own router over the route specs in mount order, HEAD read as GET) and checks the response against that route's error map (check_route_error): an error status the map lacks, or a body off the status's schema, is logged. A 500 internal_error and a 503 service_unavailable are always accepted, a JSON-RPC error envelope on a jsonrpc route is not a REST error body, a non-JSON response is skipped, and so is a request no route spec matches: the unmatched-route handler's 405 and 404 (server/unmatched_route.ts) answer for no route, so no route's map can hold them.

    Logs, never throws — a throw inside it, its logger's included, is swallowed — and leaves the response unchanged. Outside DEV create_dev_route_error_check returns null and nothing is mounted.

  • http/dev_set_cookie_check.ts

    The DEV-only Set-Cookie check: an outer middleware that logs a response which does not lead with the Set-Cookie line a middleware put on the context for every response.

    A middleware that writes a line on the context's prepared headers — the session middleware's clear of a stale cookie — records it under EXPECTED_FIRST_SET_COOKIE_KEY. Every response built through the context then carries it first: every route result, which the spine emits there, and every middleware and catch layer answering with c.json or c.text. A response built past the context does not — a consumer's post_route_middleware, a transform_middleware layer, or a raw Hono route answering with a Response it made — and only a check of the finished response can see that, so this one runs after the request: when a line was recorded, the response's first Set-Cookie must be that line, else it logs an error naming the method and path, and whether the response carries no Set-Cookie or another one first.

    One response is skipped: an accepted WebSocket upgrade's placeholder. No runtime adapter hands Hono a 101 — @hono/node-server's and @hono/bun's upgradeWebSocket return a bodiless 200 and the runtime writes the real 101 itself — so the check recognizes the placeholder by its shape: a request with Upgrade: websocket answered 200 with no body. That placeholder is no response a client reads, and no layer builds it through the context. The cost: a raw route answering a bodiless 200 to an upgrade request it did not accept goes unchecked too.

    Generic: it knows a line and an order, nothing of sessions. A sibling of the DEV error check (http/dev_route_error_check.ts) rather than part of it, as that one reads the route a request reached and only its error answers, where this one holds every answer of every path, routed or not. Mounted outermost beside it by create_app_server. Logs, never throws — a throw inside it, its logger's included, is swallowed — and leaves the response unchanged. Outside DEV create_dev_set_cookie_check returns null and nothing is mounted.

  • http/header_lines.ts

    A request header as the lines the client sent — one field value per header line, in order — where the Fetch Headers a handler normally reads has already folded them into one string.

    The credential readers (auth/credential_headers.ts) and the gate readers (http/request_headers.ts) decide on the lines: a credential header sent twice is discarded, an Origin or Host sent twice is refused, and that takes knowing it was sent twice.   • http/host.ts

    Host verification — refusing requests addressed to a name the server doesn't answer to, which is how DNS rebinding reaches a loopback server.

    In a rebinding attack, a page on an attacker's domain re-resolves that domain to 127.0.0.1 and talks to the local server same-origin: its GETs carry no Origin header, so the origin allowlist (http/origin.ts) doesn't apply. The Host header gives it away — the browser sets it from the URL, so it names the attacker's domain, never localhost.

    A host is allowed when its name is loopback (localhost, 127.0.0.0/8, [::1]), at any port — a rebinding page can't put one of those in Host — or when an allowed origin names it (the allowlist is where the server's UI is served from, so its hosts are the server's own names). Matching reuses the origin matchers, so http://localhost:* or https://*.fuz.dev admit the hosts they'd admit as origins.

    A request without a Host header passes: browsers always send one, so its absence means a non-browser client, which the auth stack governs. An empty Host and more than one Host are refused (RFC 9112 §3.2), read from the lines the client sent (get_header_lines) — on @hono/node-server a WebSocket upgrade's own Headers keep only the first Host line, and on a runtime that joins repeated lines (a, b) the comma names no host.

    The gate is on by default (AppServerOptions.host_gate). A refusal is said in the log as well as answered: the first in each HOST_REFUSAL_WARN_INTERVAL_MS is a warning naming the refused Host (quoted ASCII-only and truncated, since the client wrote it) and the env var that lists the server's names, with a count of the refusals the interval held back. The response says neither, so a client learns nothing about the allowlist.

    Twin of the Rust spine's fuz_http::host.

  • http/ip_canonical.ts

    IP address canonicalization — collapse equivalent string forms into a single key per RFC 5952 (IPv6) plus the dotted form for IPv4-mapped IPv6 addresses.

    Why this exists. Without canonicalization, the four representations ::1, ::01, ::0001, and 0:0:0:0:0:0:0:1 are the same IPv6 address but produce four distinct strings — so an attacker rotating equivalent forms behind a trusted-passthrough proxy could defeat per-IP rate limiting (each form gets a fresh bucket) and pollute audit_log.ip forensics. The collision can extend to IPv4-mapped IPv6 forms (::ffff:127.0.0.1 vs 0:0:0:0:0:ffff:7f00:1 vs the bare 127.0.0.1) — three keys for one address.

    Canonicalization runs through canonicalize_ip which:

    1. Lowercases and char-set filters (IP_LITERAL_CHARS) — non-IP strings ('unknown', 'attacker:controlled', '::1\n') pass through unchanged so downstream strict validators can still reject them.
    2. Parses with parse_ipv4_bits / parse_ipv6_bits — the grammar of Rust's IpAddr::from_str, which the spine parses with.
    3. Re-emits the canonical RFC 5952 string (lowercase hex, longest-zero-run compressed, IPv4-mapped emitted in the dotted form mandated by RFC 5952 §5).
    4. Strips the ::ffff: prefix from dotted IPv4-mapped forms so the bucket collapses to plain IPv4 — the strip moves AFTER canonicalization because the dotted form is the only form the strip can recognize symmetrically.

    Mirrors the Rust spine's fuz_http::normalize_ip, which uses the same parse-then-canonicalize-then-strip ordering for the same rate-limit-key-poisoning surface.

    rate_limit_ip_key is the bucket key an IP-keyed rate limiter uses: an IPv6 address collapses to its /64, the smallest block a host is commonly assigned, so rotating through one's own subnet buys no fresh budget. Only the limiter call sites apply it — the client IP stays the full address everywhere else (audit rows, token last_used_ip, REMOTE_ADDR).

    The module imports nothing: the action dispatcher keys its IP limiter through it, so it must not pull the optional hono peer.

  • http/json_text.ts

    JSON text read as the Rust spine's serde_json reads it.

    JSON.parse accepts three things serde_json refuses: an escaped lone surrogate ("\ud800", in a string or a key), a number out of f64 range (1e400, which JSON.parse reads as Infinity), and nesting 128 deep or more. Accepted, they don't survive storage: a lone surrogate is written to a text column as U+FFFD and refused by a jsonb one, and Infinity serializes as null. parse_json_text refuses all three, so a request body or frame gets the same verdict on both spines (invalid_json_body for a REST body, parse_error for a JSON-RPC body or frame, invalid_params for GET /rpc's params).

    The check is one linear pass over the text after JSON.parse accepts it (is_serde_json_text): a few milliseconds a MiB, whatever the text holds.

    "\u0000" is not refused here: both parsers accept it. Postgres refuses it, so the input steps do, as an invalid value rather than invalid JSON (scan_json_value in http/schema_helpers.ts).

  • http/jsonrpc.ts

    JSON-RPC 2.0 envelope schemas for RPC dispatch and SAES transport.

    Params are object-only following MCP (no positional arrays); per-action spec.input narrows further. Result is any value per spec §5 ("determined by the method invoked") — the per-action spec.output is the actual contract, so an action whose output is null or a string travels in the same envelope as one whose output is an object.

    The envelopes are loose_objects: JSON-RPC and MCP both extend them with members a reader passes over, so an unknown key is kept rather than refused. A parse returns the frame itself, not a copy.

  • http/origin_wildcard.ts

    Wildcard allowlist entries — refused at server assembly unless the operator opts in (FUZ_ALLOW_ORIGIN_WILDCARDS=true), and said aloud on every boot that admits them. Twin of the Rust fuz_http::origin_wildcard, word for word.

    Wildcards are origin syntax an operator may want, but each one admits pages the server does not serve, and the server trusts them all. The forms, as parse_allowed_origins matches them (OriginWildcard):

    • port (:*) — the host at any port, or none;
    • host — each * label is any one label, in any position (https://*.example.com, https://example.*), and a host that is all * labels (http://*, https://*.*) is every host with that many labels — four of them cover every IPv4 address;
    • both (http://*:*, https://*.example.com:*).

    A bracketed IPv6 host is exact, so it takes only the port form.

  • http/origin.ts

    Request source verification middleware for API protection.

    Verifies requests carry an Origin the server allows, or none. The origin check is one of three CSRF layers, beside SameSite: strict session cookies (auth/session_middleware.ts) and the JSON-only POST refusal (http/simple_request.ts): SameSite alone admits same-site pages, which include every other port on the same host, and the origin check refuses an untrusted page's request before any handler runs. It is the only one of the three that guards the WebSocket upgrade, which is never preflighted.

    The allowlist grammar is shared with the Rust spine entry for entry: parse_allowed_origins accepts and refuses the same entries, naming each refusal with the same AllowedOriginsErrorKind string, and an accepted list matches the same origins. The shared conformance table (testing/cross_backend/origin_conformance.json) pins both.

  • http/pending_effects.ts

    Two-queue side-effect machinery for request handlers.

    Handlers register fire-and-forget work in one of two queues, distinguished by their timing contract:

    • pending_effects: Array<Promise<void>> — eager. Producers push pool writes that are already in flight (failure audit rows, api-token usage tracking). The pool write is rollback-resilient by virtue of running outside the request transaction; pushing the in-flight handle lets test mode (await_pending_effects: true) await it.
    • post_commit_effects: Array<() => void | Promise<void>> — deferred. Producers go through emit_after_commit(ctx, fn); the flush middleware is the only site that ever invokes the thunk, and it does so after the request handler (and its wrapping db.transaction) returns. Used for WS sends, a revocation's connection closes, a success audit row's listener fan-out, and any work that must observe a committed transaction.

    Discard on rollback. A post_commit_effects thunk is discarded if the handler's transaction rolls back (a thrown handler) — it must not announce state that never committed. Both dispatch sites enforce this by wrapping their handler in dispatch_with_post_commit_rollback (see its TSDoc below for the full two-sided contract and the Rust-twin parity note). The eager pending_effects queue is the deliberate opposite: its pool writes run outside the transaction and intentionally survive rollback (attempt audits).

    The split exists because the two shapes encode different contracts: eager pushers are saying "wait for this work that's already started"; thunk pushers are saying "run this after the handler returns." Burying both behind one Array<PendingEffect> made c.var.pending_effects.push(x) ambiguous at the call site. With separate queues, the field name is the contract.

    A handler that opens its own transaction (a transaction: false route) runs it through transaction_with_post_commit_rollback, which discards what that transaction queued when it rolls back, even when the handler catches the failure and answers normally.

    Both RouteContext (HTTP routes) and ActionContext (RPC + WS actions) carry both queues by convention, so this module stays in http/ (every transport depends on it).

  • http/request_headers.ts

    The readers of the request headers the gates decide on — Origin (the origin check), Origin and Referer (browser context), Host (the host gate) and Content-Type (the CORS simple-request refusal) — as pure functions over header lines.

    One rule per reader, the Rust spine's fuz_http::request_headers reading the same one, and the shared table testing/cross_backend/request_header_conformance.json holding both to the same rows. Each reader takes the header's lines — one field value per header line, in the order sent, outer SP and HTAB already stripped (get_header_lines of http/header_lines.ts on a request) — so a header sent twice is something it can see.

    A malformed Origin, Host or Content-Type — an empty line, more than one line, a byte the grammar doesn't hold — reads refused, never absent: reading a malformed browser signal as no signal at all would fail open past the gate it feeds.

    Join-invariance. A runtime without a per-line view (Bun, an in-process app.request) hands the spine one line holding the repeated lines joined with , . No origin, host or media type holds a comma, so each reader refuses one anywhere in its value: the join of a repeat is then refused as the repeat itself is, and every reading is the same over the lines and over their join.

    Hono-free: lines in, a reading out.

  • http/request_target.ts

    The strict readers of the request target: the query string to its pairs, and one path segment to its text — each percent-decoded, or refused.

    An escape that doesn't decode is refused, never left literal and never replaced with U+FFFD: a % not followed by two hex digits is a malformed_escape, and decoded bytes that are not UTF-8 are invalid_utf8. A literal spelling would make %FF and %25FF one value, and a lossy one would make every invalid sequence the same U+FFFD — either way a handler reads a value the client never sent. The Rust spine's fuz_http::request_target reads by the same rule, and the shared table testing/cross_backend/request_target_conformance.json holds both to the same rows.

    The pure readers take text and are Hono-free. read_request_query_pairs and read_request_route_params apply them to a request (a type-only import of the Hono context): every read of the query or the path params in the spine goes through one of the two.

  • http/route_error_check.ts

    Whether an error response is one its route declares — the one rule the DEV error check (http/dev_route_error_check.ts) and the test helpers (assert_response_matches_spec) share.

    A JSON body at an error status (400 and up) is declared when the route's error map (resolve_route_error_map) has that status and the body parses against it. Three exemptions: a 500 internal_error and a 503 service_unavailable (ALWAYS_ACCEPTED_ERRORS), which the catch layers answer on any route and no route declares, and, on a jsonrpc route, a JSON-RPC error envelope, which no REST error definition describes. A non-JSON response, by is_json_response, is not checked at all.

    Also the hono-free route lookup the test helpers run (find_route_spec, testing/integration_helpers.ts): a route's Hono path template read segment by segment (split_route_template, parse_route_param) and compiled to a RegExp (compile_route_path), and the first route in mount order matching a request, HEAD read as GET (find_mounted_route). The DEV check, on the Hono side, looks routes up with Hono's own router (create_route_lookup); the two are pinned against Hono and each other by the route-lookup tests.

    Hono-free and esm-env-free.

    Built once per app (resolve_app_route_error_maps, carried as AppSurfaceSpec.route_error_maps) and read by every reader of a route's declared errors: the surface, the DEV error check, the test helpers, error coverage, and the attack-surface suite.   • http/route_result.ts

    What a route handler returns: a success, a failure, a raw answer described as data, or an SSE stream. A handler never builds a Response: apply_route_specs prepares the response from the result inside the route's transaction and builds it only after the commit, through the Hono context (prepare_route_response, emit_route_response in http/route_spec.ts). So every response a route spec answers carries what the middleware put on the context — the session middleware's clear of a stale cookie among it — and a Set-Cookie the handler returns rides only a success whose writes committed.

    • route_ok(value, {set_cookie?}) — value as JSON at 200, the Set-Cookie lines after any the middleware put on the context
    • route_fail(def, fields?) — the definition's body at its status, with the headers it derives (Retry-After); never a cookie
    • route_raw({status, headers?, body?}) — a status, headers, and a body written as given: an empty body, bytes, a stream, a JSON-RPC envelope
    • route_sse(stream) — the stream the route opened for this request (RouteContext.open_sse)

    A result is plain data, so domain code and shared helpers fail without the Hono context (return route_fail(REST_ROW_NOT_FOUND)), and a handler — which receives a RouteContext, never the Hono context — forwards a failure it was handed (if (!result.ok) return result).

    Hono-free: nothing here imports hono.

  • http/route_spec.ts

    Introspectable route spec system for Hono apps.

    Routes are defined as data (method, path, auth, input/output schemas, handler), then applied to Hono. The attack surface is generated from the specs — always accurate, always complete. A handler returns a result (http/route_result.ts) and apply_route_specs builds the response; a spec is made by define_route (or define_route_shape + attach_route_handler), which checks the handler's results against the route.

    Input/output schemas align with SAES ActionSpec conventions, and each is a @fuzdev/fuz_schema schema (AnySchema):

    • input: the request body schema (literal(null) for no body)
    • output: the success response body schema
    • a strict object for inputs (reject unknown keys): object

  • http/simple_request.ts

    Refusing CORS simple requests — the cross-origin POSTs a browser sends without asking first.

    A cross-origin fetch or form POST skips the CORS preflight when its Content-Type is absent or one of the three CORS-safelisted types (text/plain, application/x-www-form-urlencoded, multipart/form-data). The browser sends such a request as-is, with whatever cookies apply — only the response is withheld from the page. Any other content type makes the browser send an OPTIONS preflight first, and since fuz_app answers no preflight with CORS headers, the real request is never sent.

    The session cookie's SameSite=Strict doesn't close this on its own: same-site ignores the port, so a page on http://localhost:8000 is same-site with a server on http://localhost:4460 and its requests carry the cookie. The origin allowlist (http/origin.ts) refuses such a page unless a wildcard (http://localhost:*) admits it; this gate refuses it whatever the allowlist says.

    So every POST route carries a content-type check, run first by apply_route_specs (is_post_content_type_refused, 415 unsupported_content_type): a JSON route takes only application/json, bodyless or not, and a raw_body route takes any well-formed type that isn't safelisted. Both read the Content-Type lines the client sent through read_content_type (http/request_headers.ts), so a second line, or an empty one, is refused on every runtime. Only POST needs it: PUT, PATCH, and DELETE are never simple methods, so the browser always preflights them.

    The check rests on the server answering no preflight. A consumer that adds CORS middleware granting cross-origin requests reopens what this closes.

    Twin of the Rust spine's fuz_http::simple_request: the same predicates, is_json_content_type checked in each spine JSON handler and is_cors_simple_content_type by the simple_request_layer consumers mount over routes with other bodies.
