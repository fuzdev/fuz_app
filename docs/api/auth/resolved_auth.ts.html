auth/resolved_auth.ts

The account-grain credential a request resolved to, and the re-check a long-lived connection runs on it once it is registered.

The auth middleware chain resolves at most one credential per request — daemon token, then session cookie, then bearer, the first that authenticates winning — and leaves it on the Hono context as one value, ResolvedAuth (RESOLVED_AUTH_KEY, read with get_resolved_auth). Every reader takes that value, so the connections that outlive their request — a WebSocket, an SSE stream — carry it past the handshake, re-read it with revalidate_resolved_auth (or the whole admission re-check, recheck_admission), and close at its credential_deadline.

recheck_admission

(deps: QueryDeps, input: RecheckAdmissionInput): Promise<AdmissionRecheck> import {recheck_admission} from '@fuzdev/fuz_app/auth/resolved_auth.js';

Re-read everything a long-lived connection's gates read, once the connection is registered pending — the admission step a WebSocket upgrade and the audit stream share (twin of the Rust spine's admission re-check).

In order, stopping at the first refusal:

  1. The credential (revalidate_resolved_auth) → 'credential_revoked'.
  2. The acting actor the gates resolved, when there is one: it must still be an active actor of the account → 'actor_inactive'. A soft-deleted actor keeps its account's credentials and its own grant rows, so neither other re-read would refuse it.
  3. The role, when required_roles is non-empty: the acting actor's grants read afresh (refresh_role_grants), a global grant of any listed role admitting → 'role_revoked'. A scoped grant never admits at a role gate.

Every read must see what committed before it started, so deps.db is the pool-level Db (see revalidate_resolved_auth).

One arm per credential type, each carrying only what belongs to it: the session hash on a session, the token id and scope on an API token, so a session with a narrowed scope or a bearer with a session hash cannot be built. revalidate_resolved_auth
#

auth/resolved_auth.ts view source

(deps: QueryDeps, resolved: ResolvedAuth): Promise<boolean> import {revalidate_resolved_auth} from '@fuzdev/fuz_app/auth/resolved_auth.js';

Re-check that a resolved credential still authenticates: true when it does, false when it has been revoked, has expired, or its account is gone.

For a connection that outlives its request — a WebSocket, an SSE stream — and is authorized once, at open. Such a connection is closed on revocation by identity, but only once it is *registered*; between the credential read and the registration a revocation closes nothing. So the opener registers first (un-admitted — ConnectionRegistry.register_pending / SseRegistry.subscribe_pending), then calls this, then admits. A revocation that committed before this read is seen by it; one whose close ran after the registration found the pending entry.

That needs each statement here to see everything committed before it started, so deps.db must be the pool-level Db (autocommit) or a READ COMMITTED transaction — never a REPEATABLE READ / SERIALIZABLE transaction opened before the registration, whose snapshot would predate it.

What is re-read, per credential — each through the same predicate the resolve path used, so the two cannot disagree about what "valid" means (the session and account legs call the middleware's own queries; the token leg shares its WHERE fragment):

  • Session — the auth_session row still exists, is unexpired, and belongs to the resolved account.
  • API token — the api_token row still exists, is unexpired, and belongs to the resolved account (by id; the raw token is not kept).
  • Daemon token — nothing of its own. The token has no row, and no revocation event: rotation closes no connection, so there is no close an opening connection could have missed. Its keeper account is still re-read.
  • Every credential — the account row still exists and is not soft-deleted.

It re-checks the credential, not what a revocation chose to close: a logout closes every connection of the account but deletes only its own session, so another session's connection opening concurrently passes this check and is refused only if that account-wide close found its pending registration — the same two outcomes an already-open connection has.

No side effects. Unlike the bearer middleware this never touches api_token.last_used_at / last_used_ip — re-checking a credential is not using it — and it writes nothing else.

The twin of the Rust spine's revalidate_resolved_auth.
