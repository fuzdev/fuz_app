auth/role_grant_offer_queries.ts

Role grant offer database queries.

Covers the offer side of the consentful-role-grants flow: create (with re-offer upsert), decline, retract, list, find-pending, sweep-expired, and the atomic query_accept_offer that bridges offer → role_grant.

IDOR guards are expressed in each helper's signature — decline/accept require the recipient's to_account_id, retract requires the grantor's from_actor_id.

BuiltinOfferRefusal

type "bootstrap_only" | "scoped" | "grantor_not_authorized"

import type {BuiltinOfferRefusal} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Why query_accept_offer refused to mint a builtin-role grant.

Each is a row no current grant path creates but a database can still hold (a direct query_role_grant_offer_create call, or an offer made under a since-closed path), so accept — the chokepoint where an offer becomes a role_grant — checks them itself.

  • bootstrap_only — the offer is of keeper, which is bootstrap-only: never conferred through an offer, whoever made it.
  • scoped — the offer binds a builtin role to a scope; builtin roles are global-only.
  • grantor_not_authorized — the grantor no longer holds an active global admin on an active actor of an active account. Conferring a builtin role is global-admin authority, so it is re-checked when the grant is minted, not only when the offer was made.

query_accept_offer
#

auth/role_grant_offer_queries.ts view source

(deps: QueryDeps, input: AcceptOfferInput): Promise<AcceptOfferResult> import {query_accept_offer} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Accept an offer atomically: mark accepted, insert the role_grant, stamp resulting_role_grant_id, supersede sibling pending offers for the same (to_account, role, scope), and emit role_grant_offer_accept + role_grant_create + one role_grant_offer_supersede per sibling. Must run inside a transaction — the caller's route spec should declare transaction: true (or wrap explicitly).

Idempotent on replay and on race: a call that observes the offer already accepted returns the existing role_grant (created: false) rather than creating a duplicate or throwing — while that grant is still held. A grant revoked since the accept, or gone, makes the offer terminal.

Lock order — accounts, then offers, then the grant: the recipient's account row (and, for an unscoped admin offer, the grantor's) in id order (query_account_lock_for_offer_accept), then the offer and the pending siblings it supersedes in one id-ordered claim, then the grant insert. The accounts first, as every removal of either account takes them first, so a removal and an accept never meet at the offers, the actor, or a grant a purge's cascade reaches; two accepts by one recipient take turns. The offers in id order, as every transaction that writes several offer rows locks them all first in one id-ordered statement (a delete, a purge, a revoke, the expiry sweep). The grantor's authority is read unlocked after the grantor's account lock — the invariant it rests on: every write that ends a grantor's global admin takes the grantor's account row first (a revoke of the grant through query_account_lock_for_revoke, whether or not its last-admin guard ran; a delete through its write of the row; a purge through query_account_lock_admins_for_purge and query_account_lock_for_purge; the DB browser's delete, which takes none of them, excepted).

Error map:

  • RoleGrantOfferNotFoundError — offer does not exist, or belongs to a different recipient (IDOR guard). The offer row is untouched.
  • RoleGrantOfferRecipientNotActiveError — the recipient's account was deleted or purged since the caller's credential was read.
  • RoleGrantOfferAlreadyTerminalError — offer is declined, retracted, or superseded; or accepted, and its grant revoked, gone, or bound to another actor.
  • RoleGrantOfferExpiredError — offer is pending but past expires_at.
  • RoleGrantOfferActorMismatchError — actor-targeted offer, different actor.
  • RoleGrantOfferBuiltinRefusedError — a builtin-role offer that must not mint: keeper at all, a builtin bound to a scope, or one whose grantor no longer holds an active global admin (read under the grantor's account lock). The offer stays pending.

Sibling supersede is what closes the "accept a pre-revoke sibling offer to bypass a revoke" path: once A is accepted, B/C/... can no longer be accepted even if the resulting role_grant is later revoked.

query_revoke_role_grant

(deps: QueryDeps, role_grant_id: Branded<string, "Uuid">, actor_id: Branded<string, "Uuid">, revoked_by: Branded<string, "Uuid"> | null, reason?: string | ... 1 more ... | undefined): Promise<...> import {query_revoke_role_grant} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Revoke a role_grant by id, constrained to a specific actor, and end the pending offers the grant stood behind — the one supersede rule every revoke follows, the admin role_grant_revoke, a self-service disable, and a consumer's direct call alike.

Requires actor_id to prevent cross-account revocation (IDOR guard). Returns null if the role_grant is not found, already revoked, or belongs to a different actor.

Two sets of offers end with the grant, in the same transaction:

  • the revokee account's pending offers of the grant's (role, scope) — an offer accepted after the revoke would hand the role straight back;
  • every pending offer the revokee's actor made, whatever its role — an offer records no authority, so one made under this grant would still confer on accept.

Locks follow the class order (accounts, then offers, then grants): the revokee's account row (query_account_lock_for_revoke), which keeps any new offer to or from the account out and any accept by it waiting, then both sets of offers in one id-ordered statement (query_role_grant_offer_lock_for_revoke), then the grant's update — an accept claims its offers before it inserts its grant, and that insert waits on an uncommitted update of the same grant, so the grant first and the offers second would close a cycle. The two supersedes then write only rows the transaction holds. Twin of the Rust fuz_auth::role_grant_offer_queries::query_revoke_role_grant.

query_role_grant_offer_create
#

auth/role_grant_offer_queries.ts view source

(deps: QueryDeps, input: CreateRoleGrantOfferInput): Promise<RoleGrantOffer> import {query_role_grant_offer_create} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Create a new role_grant offer, or refresh an existing pending offer for the same (to_account_id, role, scope_id, from_actor_id) tuple.

Re-offer semantics: a second call by the same grantor with the same (to_account, role, scope) while pending upserts the existing row, refreshing message and expires_at (and to_actor_id — supplying a different to_actor_id on re-offer narrows the existing row to the named actor; supplying null widens it back to account-grain) and clearing expire_audited_at, so a re-offer of an expired, already-audited row gets its own role_grant_offer_expire when the refreshed expiry passes. A different grantor offering the same (to_account, role, scope) creates a distinct row — multiple pending grantors coexist. After a terminal state, a re-offer is a fresh INSERT.

Self-offer rejection: throws RoleGrantOfferSelfTargetError if the offering actor belongs to the recipient account.

Actor-targeted offers: when to_actor_id is supplied, query_accept_offer rejects any actor other than the named one. Closes the audit hole where offer-shape events would otherwise leave target_actor_id null even when the recipient binding is known at offer time. A named actor must be an active actor of to_account_id.

Both parties must be active accounts, checked here so every caller — the spine's handler and a consumer creating offers on its own path — gets the rule. Both account rows are read under FOR SHARE before the insert, in one statement in id order (query_account_lock_live_many): an account delete writes its tombstone first, so a delete committed before the read is waited for and seen (the offer is refused), and one after it waits for this transaction to commit and then supersedes the offer with the party's others. Run it inside the caller's transaction, which the lock spans. The self-target check comes first, so an offer to one's own account is refused as that whatever else it names.

Lock every pending offer an account removal supersedes — the ones its actors made and the ones made to it — in one statement, in id order.

A delete or a purge writes those offers in two statements, the outgoing then the incoming; taken that way, each could hold rows another writer of both sets (a revoke of the account's grant, the expiry sweep) waits on while waiting on rows that writer holds. Locked together first, in the order every multi-row offer write takes its rows, the two supersedes then write rows this transaction already holds. No offer to or from the account can be made meanwhile: an offer create takes both parties' account rows, which the removal has written or locked. query_role_grant_offer_sweep_expired
#

auth/role_grant_offer_queries.ts view source

(deps: QueryDeps): Promise<RoleGrantOffer[]> import {query_role_grant_offer_sweep_expired} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Claim the pending offers whose expires_at has passed and whose expiry has not been audited yet, stamping expire_audited_at on each, and return them soonest-expiry first.

The stamp is the sweep's idempotency: a claimed row never matches again, so each expiry is audited exactly once. It must share a transaction with the caller's role_grant_offer_expire audit inserts — committed together, or rolled back together so the next sweep retries. Concurrent sweeps claim disjoint rows: a row another sweep has stamped but not committed blocks on its row lock, then fails the re-checked expire_audited_at IS NULL. The rows are locked in id order (offer_rows_locked_in_id_order), as every multi-row offer write takes them, so a sweep and a delete, purge, revoke or accept over the same expired offers never wait on each other in opposite orders. cleanup_expired_role_grant_offers is the caller.

import {RoleGrantOfferRecipientNotActiveError} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Error thrown when the recipient is not an active account.

By query_role_grant_offer_create: to_account_id names no account, a soft-deleted one, or one with no active actor. A deleted recipient and one that never existed are the one refusal, so a caller learns nothing from it that a missing id wouldn't tell; the handler answers it as role_grant_assign answers the same recipient. By query_accept_offer: the accepting account — the caller — was deleted or purged after its credential was read, and its handler answers the dead credential. Twin of the Rust RoleGrantOfferError::RecipientNotActive.

import {RoleGrantOfferSelfTargetError} from '@fuzdev/fuz_app/auth/role_grant_offer_queries.js';

Error thrown when a grantor attempts to offer a role_grant to their own account.

Enforced via a single SELECT on the grantor's actor.account_id (rather than via a CHECK constraint or a denormalized column). Resolving from the grantor side keeps the check multi-actor-correct: under multi-actor the recipient account may host many actors, but the grantor → account binding remains 1:1 by definition of actor.
