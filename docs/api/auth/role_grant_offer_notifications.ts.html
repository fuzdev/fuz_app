auth/role_grant_offer_notifications.ts

Role grant offer WebSocket notification specs, builders, and the helpers the handlers queue them with (queue_offer_notification, queue_supersede_notifications).

These RemoteNotificationActionSpecs cover the consentful-role-grants lifecycle events the server pushes to affected accounts:

  • role_grant_offer_received → recipient's sockets when an offer is created
  • role_grant_offer_retracted → recipient's sockets when a grantor retracts
  • role_grant_offer_accepted → grantor's sockets when the recipient accepts
  • role_grant_offer_declined → grantor's sockets when the recipient declines
  • role_grant_offer_supersede → each live party to a pending offer a cascade ended — a sibling accept, a revoke, an account removal — but the one the cascade's own answer or socket close already covers
  • role_grant_revoked → revokee's sockets when one of their active role_grants is revoked by the role_grant_revoke action (companion to the role_grant_revoke audit event)

Payloads are flat and normalized — RoleGrantOfferJson for the offer-lifecycle notifications (decline reason rides on offer.decline_reason, not a sibling field), and {role_grant_id, role, scope_kind, scope_id, reason} for role_grant_revoked. The revokee/grantor/recipient account id travels via the send target (the NotificationSender.send_to_account argument), not in the payload. The params schemas are @fuzdev/fuz_schema schemas.

role_grant_offer_notification_actions holds the specs as handler-less actions. to_ws_actions (actions/protocol.ts) appends them to the WS action set of an RPC list that carries the role_grant_offer actions, so the surface lists them on the WS endpoint as remote_notification methods. An inbound frame for one is still answered method_not_found, as no handler is registered. Under DEV, perform_action hands every action handler a sender wrapped in create_validated_notification_sender, so each params object sent is checked against its spec's input; production sends unchecked.

Params for role_grant_offer_supersede, sent to a party of a pending offer a cascade ended: a sibling accept (reason: 'sibling_accepted'), a revoke of the recipient's grant or of any grant of the grantor's actor (reason: 'role_grant_revoked'), or the removal of either party's account (reason: 'account_deleted'). cause_id points at the accepted offer, the revoked role_grant, or the removed account respectively — the cause_id of the offer's role_grant_offer_supersede audit row — except on a recipient's frame of its grantor's account removal, where it is the offer's grantor actor (from_actor_id), an id the recipient already holds. The audit metadata's reason set is wider: a consumer's scope teardown audits scope_destroyed, which no notification carries.

auth/role_grant_offer_notifications.ts view source

SupersedeAudience import type {SupersedeAudience} from '@fuzdev/fuz_app/auth/role_grant_offer_notifications.js';

Which parties of a superseded offer a cascade tells, and the cause_id each is sent; null leaves that party out. A party the cascade's own answer covers (the accepting recipient) or whose account it removes (its connections close) is left out by the call site, which knows which side that party is on. A recipient told of its grantor's account removal is sent the grantor's actor, never the account id, which no recipient sees otherwise. Twin of the Rust SupersedeAudience.
