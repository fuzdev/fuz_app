auth/session_cookie.ts

The signed session cookie: its name, value format, verification, and the exact Set-Cookie strings that set and clear it — byte for byte the Rust spine's fuz_auth::session_cookie.

Cookie value: keyring.sign("${session_token}:${expires_at}"). The signed payload carries the raw session token (whose blake3 hash is the auth_session row id) and its expiry, so one HMAC covers both the token bind and the freshness check.

parse_session_from_cookies
#

auth/session_cookie.ts view source

(cookie_lines: readonly string[], keyring: Keyring, cookie_name: string, now_seconds?: number | undefined): Promise<SessionCookieRead> import {parse_session_from_cookies} from '@fuzdev/fuz_app/auth/session_cookie.js';

Read the session cookie out of a request's Cookie lines: the cookie_name pair (read_session_cookie_value — the first, verbatim), verified under the keyring, its signed expiry checked, its session token answered with that expiry.

The three answers are what the cookie alone shows (SessionCookieRead). An empty value (name=) is a cookie sent with none: present and invalid. A valid cookie whose auth_session row is gone is still valid here; nothing clears it. There is deliberately no refresh: a re-sign would compute a fresh expiry past the row's fixed expires_at, so the lifetime is the one signing at mint, on both spines.

Twin of the Rust parse_session_from_cookies, which takes the request's headers.

SESSION_AGE_MAX
#

auth/session_cookie.ts view source

number import {SESSION_AGE_MAX} from '@fuzdev/fuz_app/auth/session_cookie.js';

Cookie max age in seconds (30 days — aligned with AUTH_SESSION_LIFETIME_MS).

This is an absolute session lifetime: the cookie is signed once at mint (expires_at = mint + SESSION_AGE_MAX) and never re-signed, matching the DB row's fixed expires_at. There is deliberately no sliding renewal on either leg — see docs/security.md §Session Security.

"Path=/; HttpOnly; Secure; SameSite=Strict" import {SESSION_COOKIE_ATTRIBUTES} from '@fuzdev/fuz_app/auth/session_cookie.js';

The attributes every session Set-Cookie carries, in the order written — the Rust spine's SESSION_COOKIE_ATTRIBUTES, byte for byte. Fixed: the spine writes one cookie.

  • Path=/ - sent to every path of the origin
  • HttpOnly - out of reach of page script
  • Secure - HTTPS only (Chrome and Firefox treat localhost as secure)
  • SameSite=Strict - never sent on a cross-site request

SessionCookieRead
#

auth/session_cookie.ts view source

SessionCookieRead

type { kind: "absent"; } | { kind: "invalid"; } | { kind: "valid"; cookie: SessionCookie; }

import type {SessionCookieRead} from '@fuzdev/fuz_app/auth/session_cookie.js';

How a request's Cookie lines read for the session cookie — what the cookie alone shows, before any database work. Twin of the Rust SessionCookieRead.

  • absent — no pair names the cookie
  • invalid — a pair names it and its value fails verification: unreadable, a bad MAC, a signed expiry that has passed, an empty token, an empty value. What the session middleware clears.
  • valid — it verifies under the keyring and its signed expiry is ahead. Says nothing about the auth_session row.
