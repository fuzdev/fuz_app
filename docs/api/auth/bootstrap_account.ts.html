auth/bootstrap_account.ts

Bootstrap flow for creating the first account.

Uses an atomic bootstrap_lock table to prevent TOCTOU race conditions. The lock flip, the account, its keeper and admin grants, its session, and the burn of the one-shot token file all happen in one transaction, the burn last — so a live token never outlives a successful bootstrap, and a bootstrap whose token can't be burned never happened.

(deps: BootstrapAccountDeps, ctx: BootstrapAccountContext, provided_token: string, input: BootstrapAccountInput, options: BootstrapAccountOptions): Promise<...> import {bootstrap_account} from '@fuzdev/fuz_app/auth/bootstrap_account.js';

Bootstrap the first account with keeper and admin privileges.

  1. Read and verify the bootstrap token (before the transaction) — the file's raw bytes less one optional trailing LF, at least BOOTSTRAP_TOKEN_MIN_BYTES long, compared in constant time
  2. Hash the password (CPU-intensive, before the transaction)
  3. In one transaction: flip the bootstrap_lock atomically (zero rows is the race loser, already_bootstrapped, nothing burned); create the account + actor; grant keeper and admin (no expiry, `granted_by = null`); mint the session through the capped minter login uses (the cap evicts nothing on a new account) and format its Set-Cookie line; write the bootstrap success audit row; then burn the token file, last, just before the commit

The burn comes after the lock, so only the lock winner burns (its row lock is held across the unlink, so a concurrent attempt waits on its UPDATE); after the inserts, so a failed insert spends nothing; last, so the window between a burn and a failed commit is one round trip. The audit row is written before the burn, so a refused row rolls the bootstrap back with the token unburned and the window open, as a failed insert does; its listener fan-out is discarded with any rollback. A burn that fails rolls everything back and answers token_file_undeletable: nothing was created and the token is still valid, so the operator fixes the directory and retries. A commit that fails after the burn is logged as an error — the token is gone and a new one must be written. Twin of the Rust bootstrap_handler.

BOOTSTRAP_TOKEN_MIN_BYTES
#

auth/bootstrap_account.ts view source

32 import {BOOTSTRAP_TOKEN_MIN_BYTES} from '@fuzdev/fuz_app/auth/bootstrap_account.js';

The fewest bytes a bootstrap token holds, counted after its one optional trailing LF. A shorter file is read as unreadable: an empty or "\n" file would otherwise leave bootstrap advertised as open while nothing can ever match it, and a short token is guessable. Every generator writes more (32 random bytes as 64 lowercase hex characters); the readers accept any bytes that clear this floor. Twin of the Rust BOOTSTRAP_TOKEN_MIN_BYTES (fuz_auth).

(deps: Pick<BootstrapAccountDeps, "log" | "token_store">): Promise<Uint8Array<ArrayBufferLike>> import {read_bootstrap_token} from '@fuzdev/fuz_app/auth/bootstrap_account.js';

Read the bootstrap token the way both the availability check and the request-time compare need it: the store's hardened read, less one trailing LF, refused when shorter than BOOTSTRAP_TOKEN_MIN_BYTES. A short token logs an error naming the file before the throw — it is a misconfiguration the operator must fix, never a quiet "unavailable". Twin of the Rust bootstrap_token_from_file.
