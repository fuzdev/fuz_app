auth/role_grant_offer_actions.ts

Role grant offer RPC action handlers — the consentful-role-grants action surface.

The offer-lifecycle methods (create / accept / decline / retract / list / history) plus role_grant_revoke and role_grant_assign (both admin-only). All mount on a consumer's JSON-RPC endpoint through rpc_endpoints. The action specs themselves live in auth/role_grant_offer_action_specs.ts. Mutations declare side_effects: true so the RPC dispatcher wraps the handler in a DB transaction; role_grant_offer_list and role_grant_offer_history declare side_effects: false so they are addressable via GET.

Authorization:

  • role_grant_offer_create — the role's grant_paths must include 'admin', and by default the grantor must hold a global admin. Consumers needing a richer policy (e.g., "teacher may offer student in *their* classroom") pass an authorize callback that overrides the default — for app roles only: a builtin role (admin / keeper) is global-only (a scoped one is refused with role_grant_builtin_scoped) and offered only by a global admin, both decided before the callback runs.
  • role_grant_offer_accept / role_grant_offer_decline — keyed to the caller's account; query_* helpers enforce the IDOR guard. Accept also refuses a builtin-role offer that must not mint (keeper, scoped, or a grantor who no longer holds a global admin), auditing the refusal and leaving the offer pending.
  • role_grant_offer_retract — keyed to the caller's actor.
  • role_grant_offer_list / role_grant_offer_history — self by default; {account_id} is admin-only.
  • role_grant_revoke — spec-level auth: {role: 'admin'}; the RPC dispatcher rejects non-admin callers before the handler runs. The admin-grant-path gate prevents revoking keeper / daemon-scoped roles via this surface. Keys on actor_id to survive multi-actor accounts.
  • role_grant_assign — spec-level auth: {role: 'admin'} (a global grant, re-checked in the handler); the immediate consent-free conferral path. The admin-grant-path gate prevents assigning keeper / daemon-scoped roles via this surface, and a scoped admin is refused. No holder-propagation — only a global admin confers; holding a role grants no power to assign it.

Audit events are emitted in-transaction by the query layer (atomic with the role_grant write on accept) or by the handler via the bound deps.audit.emit_role_grant_target helper (revoke, assign, and the single-event lifecycle transitions — a success row written in the request transaction, a failure row on the pool). audit.notify (SSE/WS broadcast) fires post-commit in both paths.

WS notifications go through the handler context's sender (ctx.notification_sender), queued post-commit (queue_offer_notification, queue_supersede_notifications): offer lifecycle transitions notify the counterparty, role_grant_revoke notifies the revokee (role_grant_revoked) plus both parties of each superseded pending offer, and an accept each superseded sibling's grantor. role_grant_revoke of a global grant also closes the revokee's connections gated on the role through deps.connection_closer, after the commit.

Options for create_role_grant_offer_actions.

roles?

Role registry from create_role_registry(). Defaults to builtin roles only. Drives the grantability gate: a role is offerable / revocable through this surface only when its RoleSpec.grant_paths includes 'admin' (the GRANT_PATH_ADMIN constant).

type RoleRegistry

default_ttl_ms?

TTL applied to newly-created offers. Defaults to ROLE_GRANT_OFFER_DEFAULT_TTL_MS.

type number

authorize?

Custom authorization for role_grant_offer_create and role_grant_assign. The default requires the caller to hold a global admin grant; the role's RoleSpec.grant_paths must include 'admin' either way. Consumers with richer policies (scope-aware, chained roles) override this. A builtin role never reaches the callback unless the caller holds a global admin and the offer is unscoped — the spine decides builtin-role offers itself, so a callback needs no builtin handling of its own.

RoleGrantOfferCreateAuthorize import type {RoleGrantOfferCreateAuthorize} from '@fuzdev/fuz_app/auth/role_grant_offer_actions.js';

Authorization callback for role_grant_offer_create and role_grant_assign. Returns true to allow, false to reject (handler converts to forbidden with role_grant_offer_not_authorized).

Provided with the fully-resolved request context and the parsed input (pre-TTL, pre-normalization). Consumers override the default to implement policies like "teacher may offer classroom_student only in classrooms they teach". role_grant_assign — the global-admin path that confers a grant with no offer — runs it too, so a policy over which grants may exist (a role that must be scoped, a scope that must be real) holds on both paths. Twin of the Rust OfferCreateAuthorize.

An offer authorized by a scoped grant must stay at that grant's scope: a scope teardown (query_role_grant_revoke_for_scope) supersedes only that scope's offers, so a revokee's offers elsewhere survive it.

ctx is the request's: both verbs have side effects, so ctx.db is the request transaction, and a callback needing the database (a scope-existence check, say) reads through it. Read-only — the callback decides, it never writes; a write would commit or roll back with the request, and nothing enforces this but the callback.
