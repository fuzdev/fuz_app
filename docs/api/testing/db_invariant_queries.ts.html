testing/db_invariant_queries.ts

Database invariants of the auth schema — states no sequence of spine operations may leave behind, checked over the rows themselves.

A wire-level test asserts what one request answers; these hold the database a whole test leaves, so a cascade that misses a row (a session outliving its account's tombstone, an offer still pending from a deleted grantor) fails even when no request ever reads the row. One SQL set serves both spines: schema parity keeps their DDL identical.

Two kinds:

  • State — over the live rows: no credential of a tombstoned account, no pending offer or unclaimed invite with a dead party, a bootstrapped database keeps a live keeper and a live admin and an unbootstrapped one has no account, an actor's tombstone agrees with its account's, and the structural pairings the writes keep.
  • History — over audit_log, so an undelete can't hide a cascade that missed: no pending offer, unclaimed invite or live credential that a successful removal of its account should have ended.

An invite's issuer is its created_by actor's account, or — once a purge's cascade has nulled created_by — the account_id of the invite's successful invite_create audit row (metadata.invite_id; both spines write it). account_purge counts as a removal only for invites: a purge's cascade deletes the account's offers, sessions and tokens with it, so for those a purge leaves nothing to check.

Order against a removal. Where both spines audit the row's creation (role_grant_offer_create with metadata.offer_id, invite_create with metadata.invite_id, token_create with metadata.token_id), the removal's audit seq is compared with the creation row's — exact, whatever the clocks: the creation row is written under the account lock the removal takes, in the creating transaction. Otherwise (sessions, and rows written without the action, as the in-process fixture writes them) the timestamps are compared, and a removal in the same clock tick as the creation counts as after it: the database clock may tick in milliseconds (pglet), and a creation tied with the removal that should have ended it is the leak the check exists for, while the opposite order — a removal, an undelete, and a fresh creation in one tick — is not a sequence the tests drive.

The long-transaction walk. A timestamp is its transaction's start (created_at defaults to NOW()), not when the row was written, so a timestamp comparison misflags one legal sequence: a login's transaction begins, a delete and then an undelete of its account commit, and only then does the login take the account lock, find the account live, and insert — a session minted after the undelete, its created_at before the delete. Nothing drives it: the login must stall between its transaction's start and the account lock while two admin actions commit, which only a test stalling the login's connection between its BEGIN and its lock statement could arrange, on Postgres, and none does. Sessions keep this false positive: their creation is audited by login (or signup, bootstrap), whose rows carry no session_id to order by, and adding one would change an audit shape on both spines — not taken. An API token minted by account_token_create is ordered by its token_create row, so the walk can't misflag one — nor could it reach one: that mint re-reads its authorizing session under the account lock, and a delete revokes every session. A token minted without that row (a fixture, a consumer's own mint) falls back to created_at.

Not invariants, by design: the role grants of a tombstoned actor (kept through delete and undelete, inert while no credential authenticates) and expired credentials no sweep has removed.

The whole set is one statement, DB_INVARIANTS_SQL, binding the role names as $1 (keeper) and $2 (admin). db_invariants.gen.sql.ts writes it to db_invariants.sql, which the Rust spine's fuz_testing embeds byte for byte: the _testing_db_invariants backdoor runs it on either spine, so a cross-process harness checks a database it can't reach. Each violation comes back as its invariant's name and the row as JSON text (jsonb_build_object(...)::text), parsed on the reading side; exclusions filter the parsed rows (to_db_invariant_violations).

Vitest-free, so a test binary can mount the backdoor; the per-test hooks live in db_invariants.ts.

Invariants left unchecked, each by name with the non-empty reason it can't hold for the tests at hand — rows a test writes directly, without the cascade the spine would run. A test an xfail_until marker tracks breaks the invariant its gap breaks while the gap is open, and the per-test check fails it whatever the marker expects: exclude that invariant on the setup the marked test uses, with the marker's tracking id in the reason.

all turns the whole check off, with its reason, and stands alone: a cross-process backend that doesn't serve _testing_db_invariants must say so this way, and a setup refuses it otherwise.
