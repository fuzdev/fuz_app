testing/schema_generators.ts

Schema-driven value generation helpers for testing.

Walks @fuzdev/fuz_schema schemas to generate valid values for route params, request bodies, and URL paths. Used by adversarial input, adversarial 404, and round-trip validation test suites. A value that is no schema throws, and so does an input no body can be generated for, rather than yielding no body.

(object_schema: AnySchema, schema: AnySchema): GeneratedObject import {generate_valid_object} from '@fuzdev/fuz_app/testing/schema_generators.js';

Generate a valid object for an object schema: its required and defaulted fields first; when schema still refuses it, each optional field alone on top of those, in declaration order, taking the first that parses; and failing that, the optional fields added one at a time, in declaration order, until it parses. The fill covers a refine over optional fields (at least one of, exactly one of, both of), which the required-only object can't satisfy, and the single-field pass keeps an unrelated optional field declared ahead of the refined ones (an acting, a note) out of the object.

Shared by the top-level body generators and generate_valid_value's nested-object case, so a refined object validates the same way at any depth.

resolve_valid_path
#

testing/schema_generators.ts view source

(path: string, params_schema?: AnySchema | undefined, param_values?: Readonly<Record<string, string>> | undefined): string import {resolve_valid_path} from '@fuzdev/fuz_app/testing/schema_generators.js';

Resolve a route path with valid-ish param values so params validation passes. Used when testing input on routes that also have params.

The template is read as Hono reads it (split_route_template, parse_route_param): only a whole param segment — :name or :name{re}, optional or not — is filled, so a : inside a literal segment (/v1/files:upload) stays, and a {re} goes with its param. An optional param is filled too.

A value in param_values is used first, percent-encoded. Otherwise, without a params schema (or for a param the schema doesn't name) each param becomes test_<name> — fine for an unconstrained segment. With one, test_<name> is still preferred wherever the field schema accepts it, because the param name in the URL is what makes a failure message readable. Only a segment that refuses it falls through: a uuid param takes the nil UUID (the fast path — by far the most common shape), and anything else is synthesized by generate_valid_string, so a format-constrained segment (a blake3:… fact hash, a tok_… id) resolves to a value its schema accepts instead of a test_<name> that 400s before the route's real gates run. The synthesized value is percent-encoded, and a value containing / is refused (it would silently add a path segment and route elsewhere) — both fall back to test_<name>.

A {re} param's value, supplied or not, must match its pattern, grouped and anchored as Hono's RegExpRouter reads it — the stricter of its routers' readings, as TrieRouter leaves a top-level alternation ungrouped (compile_route_param_pattern, over the value as Hono decodes it, decode_route_path) — or the request would reach no route; no value is guessed from the pattern. A supplied value the URL would normalize away ('', ., ..) is refused by name.

to_field_json_schema
#

testing/schema_generators.ts view source

(field_schema: AnySchema): Record<string, unknown> import {to_field_json_schema} from '@fuzdev/fuz_app/testing/schema_generators.js';

The JSON Schema of a field's input side — where its format, pattern and bounds live.

Rendered with io: 'input', so a field carrying a transform in a pipe (Username) still yields the constraints its input is checked against; the default output side throws on a transform. A pipe yields its input side only, so constraints of the stage after it are not here. A nullable field renders as anyOf: [{…}, {type: 'null'}], or a bare type as type: [type, 'null']; its one non-null branch or type is returned, so the bounds, pattern and type read the same as on the bare field. A union of two or more non-null branches returns the whole schema — its branches' bounds are no single field's bounds.

It renders with unrepresentable: 'any': a part JSON Schema can't say (a check or a bigint) is left out or {}, and the bounds around it still read, so a pipe(string, max_length(n), check(…)) keeps its maxLength — every case the generators build from it is checked against the field itself before it's used. What the emitter refuses even then (an entry named like a member of Object.prototype, metadata that isn't JSON) throws: a mistake in the schema, not a gap in JSON Schema.

A check is never here: JSON Schema can't express one, so a bound a check enforces (a code-point length, a cross-field rule) generates no boundary case.
