testing/cross_backend/ws_endpoint.ts

Where a spawned backend's WebSocket endpoint is, and how the cross suites open a socket on it as one account's session.

The socket-driving cross suites take WsEndpointTarget as their endpoint options (flat, or nested as ws on a suite whose socket cases are optional), and open a socket on a fixture account's session through open_session_ws, so the cookie read, the missing-cookie assertion and the transport choice are written once. A refused upgrade is asserted at its status with assert_ws_upgrade_refused. Sockets on another credential — a daemon token, a bearer, a session a case logged in on its own transport — and the raw-socket cases open their own way.

Open a real-upgrade socket on target as account's session: its session cookie on the upgrade, target.origin (or base_url) as the Origin.

The cookie is the static one account.create_session_headers carries, not whatever fixture.transport's jar holds now, so a case that rotates the session through fixture.transport first upgrades on the stale cookie.

Options for open_session_ws.

inheritance

extends: Pick< WsTransportOptions, 'default_timeout_ms' | 'on_request' | 'headers' >

admitted

Round-trip heartbeat before resolving, so the backend has admitted the connection (create_admitted_ws_transport) — needed by a case that waits for a push or relies on registration order. false resolves once the socket is open (create_ws_transport), for a case that only round-trips or counts its own requests.

type boolean

readonly

headers?

Extra headers for the upgrade request — e.g. an X-Forwarded-For that a backend trusting the loopback proxy resolves as the connection's client IP, which keys the per-IP action rate limiter for every message on the socket. cookies and origin set their own headers.

type Readonly<Record<string, string>>

readonly

default_timeout_ms?

Optional per-call default for wait_for timeouts. Falls back to WS_CLIENT_DEFAULT_TIMEOUT_MS if omitted.

type number

readonly

on_request?

Optional responder for server-initiated requests (the server→client direction ActionPeer adds). Attached before the upgrade so a connect-time or on-demand peer/ping is answered as soon as it arrives. Omit for the default observe-only client — a server-initiated request is then surfaced as a normal message (today's behavior).
