testing/cross_backend/capabilities.ts

Capability vocabulary for cross-backend integration testing.

Backends declare which optional behaviors they support; suite bodies call test_if(capabilities.X, ...) to skip cases the backend doesn't implement. No if (config.name === 'rust') branches anywhere — name- checking is a code smell that says capability vocabulary is missing.

In-process Hono via default_in_process_setup declares every capability its transport can exercise (see in_process_capabilities — the cross-process-only flags stay false). Cross-process backends opt in per-flag on their BackendConfig.

Where the per-backend declarations live (this file owns only the vocabulary + the in-process preset):

  • in_process_capabilities — here; every flag true except the cross-process-only ones.
  • ts_default_capabilities / rust_default_capabilities — consumer-facing family defaults, in default_backend_configs.ts — every flag but the MountFlags (FamilyDefaultCapabilities), as full literals, so adding a non-mount capability is a compile error until each family declares it.
  • ts_spine_capabilities / ts_spine_bun_capabilities — fuz_app's own TS spine presets, in ts_spine_backend_config.ts (the family default plus every mount flag; Bun flips ws_handshake_pipelining).
  • rust_spine_stub_capabilities — fuz_app's Rust spine-stub preset, in rust_spine_stub_backend_config.ts (the rust family default plus every mount flag).

Mount flags have no default. A flag naming something a backend mounts (a MountFlag) is never inherited, nor is the testing_backdoors list: the family defaults are FamilyDefaultCapabilities, which omits them, so every backend config states each one, and describe_capability_mounts_cross_tests holds each a request can observe to what the backend mounts, false as much as true. The family defaults carry only what the family guarantees — the declared spine surface's mounts, fallback and host gate (account_lifecycle, account_status, spine_fallback, host_gate) and the runtime behavior of its reference runtime (ws_handshake_pipelining, ws_refusal_body: Node for TS, hyper for Rust), which a backend on another runtime overrides.

Gating flags only. BackendCapabilities holds only flags a suite actually gates on (each has a test_if(capabilities.X, ...) reader, or — ws_refusal_body — picks how a case reads a refusal), plus the testing_backdoors list the backdoor suite and describe_spine_cross_suites read. A wiring fact no suite reads is not a capability.

BackendCapabilities import type {BackendCapabilities} from '@fuzdev/fuz_app/testing/cross_backend/capabilities.js';

Optional behaviors a backend may support. Each flag's TSDoc names the tests that gate on it; add a new flag here before referencing it from a suite body, and document the gating tests inline. A wiring fact no suite reads doesn't belong here.

ws

WebSocket transport is reachable end-to-end. Gates the cross-process WS round-trip suite, the per-account connection-cap suite (describe_ws_connection_cap_cross_tests), and the front door's WS-path cases (describe_transport_composition_cross_tests) — the upgrade rows, and the rows that ask for no upgrade, which run in-process too; the in-process describe_ws_round_trip_tests runs against register_action_ws directly and ignores this flag.

type boolean

readonly

sse

SSE transport is reachable end-to-end. Gates the cross-process SSE suite (describe_cross_process_sse_tests — connect, audit data frame, close-on-revoke, the per-session stream cap); in-process SSE uses the on_audit_event hook and ignores this flag.

type boolean

readonly

cell_crud

Cell CRUD verbs (cell_create / cell_get / cell_update / cell_delete / cell_list) are live-mounted on the backend's RPC path and its DB carries the fuz_cell migration namespace. Gates the dedicated describe_cell_crud_cross_tests suite. Like ws / sse, cells stay off the standard declared surface — only this flag opts a backend into the cell parity coverage.

type boolean

readonly

cell_relations

The relation / ACL / audit cell verbs beyond plain CRUD (cell_grant_* / cell_field_* / cell_item_* / cell_clone / cell_audit_list) are live-mounted on the backend's RPC path. Gates the dedicated describe_cell_relations_cross_tests suite — grant lifecycle, field / item bidirectional relations, clone shallow + deep, manage-tier audit gating, and the now-reachable cell_visibility_manage_only 403 (editor-grant principal). Like cell_crud, these stay off the standard declared surface; a backend mounting only plain CRUD declares cell_crud: true, cell_relations: false.

type boolean

readonly

account_lifecycle

The account-lifecycle admin verbs (account_delete soft-delete, account_undelete reactivation, account_purge keeper hard-delete) are live-mounted on the backend's RPC path. Gates the dedicated describe_account_lifecycle_cross_tests suite.

Unlike cells / fact-serving / ws / sse, these verbs are on the standard declared surface — they live in create_admin_actions, so create_spine_surface_spec carries them and the spec-derived round-trip + attack-surface suites already auto-enumerate their wire shape + auth. This flag gates the *behavioral* parity the generic round-trip can't provide: it can't drive verbs that delete their own subject (soft-delete → undelete round-trip, keeper-confirmed purge, the keeper-guard refusal), so the dedicated cross suite adds them.

type boolean

readonly

fact_serving

The cell-gated fact-serving route (GET /api/cells/:cell_id/facts/:hash) is live-mounted on the backend, its DB carries the fuz_facts migration namespace, and it mounts the _testing_put_fact seeder — declared in testing_backdoors, which describe_spine_cross_suites requires. Gates describe_fact_serving_cross_tests' per-reference read model (cell-scoped admit via a viewable cell, cross-owner-dedup-no-leak, 404-mask), describe_cell_ref_admission_cross_tests (its grant, item, and clone cases with cell_relations), and the fact cases of the moderation suite. Like cells, the serve route stays off the standard declared surface. The admin bare-hash route is its own flag, fact_serving_admin_hash. The suite's missing-disk-file case assumes the backend serves external facts from disk: one with X-Accel delivery on hands off with a 200 (nginx would answer the missing file) and fails it.

type boolean

readonly

fact_serving_admin_hash

The admin-only bare-hash fact route (GET /api/facts/:hash) is live-mounted. Gates the bare-hash cases of describe_fact_serving_cross_tests (with fact_serving, whose seeder they use), describe_query_shape_cross_tests and describe_token_scope_surface_cross_tests. A backend serving only the cell-gated route states `fact_serving: true, fact_serving_admin_hash: false`.

type boolean

readonly

ready

The /ready readiness deploy gate (GET /ready) is live-mounted on the backend — the public column-presence schema-drift probe over the committed expected_schema.json. Gates describe_ready_cross_tests (anonymous GET /ready → 200 {ready: true} on a clean spine bootstrap). Like ws/sse/cells, the route stays off the standard declared surface (create_spine_surface_spec); this flag opts a backend into the dedicated readiness parity coverage. The drift → 503 path stays per-impl unit tests.

type boolean

readonly

account_status

The account surface serves GET /api/account/status (account info + bootstrap_available flag). Bundled into create_account_route_specs, so any backend mounting the account routes serves it — true for every spine. Gates the account status response body case in describe_standard_integration_tests: when true the case asserts the route is present (fail-loud on 404, no silent skip); when false it skips explicitly (a backend that deliberately omits the route).

type boolean

readonly

peer_request

The backend can initiate a JSON-RPC request to a connected client and await its typed reply (the server→client request/response direction ActionPeer adds). Gates describe_peer_ping_ws_tests — the on-demand peer/ping round-trip plus its security negatives (unsolicited-response rejection, per-connection id isolation, never-replying Timeout, wrong-shape reply rejection).

true on fuz_app's own spine presets — the Rust testing_spine_stub and the TS spine (ConnectionRegistry.request_connection drives the round-trip, correlated by register_action_ws). A MountFlag: a backend states true once it mounts peer/ping on a WS endpoint and the HTTP RPC endpoint (the no-transport refusal). Like ws/sse/cells, peer/ping stays off the standard declared surface (it's a protocol action, manifest-excluded), so this flag is the only opt-in into the peer parity coverage.

type boolean

readonly

ws_handshake_pipelining

The backend's HTTP server accepts WebSocket frames written in the same TCP write as the upgrade request, handing them to the socket once the handshake completes. Gates the frames sent with the handshake case in describe_cross_process_ws_tests — the deterministic form of "frames that arrive before the connection is admitted wait for admission", since those frames are in the backend's hands before it can have admitted anything.

true for Node (ws) and the Rust spine (hyper hands the leftover bytes to the upgraded stream); false for a Bun backend that upgrades after an asynchronous check, as one behind auth does — Bun.serve answers such a request 400 (observed on Bun 1.4.3). A backend without it still runs the suite's client-library case (requests sent the moment the socket opens), which pins the same contract without forcing the ordering.

type boolean

readonly

ws_account_actions

The backend's WebSocket endpoint mounts the self-service account actions (account_session_revoke_all among them), so a socket can revoke the session it is running on. Gates the self-revocation case in describe_cross_process_ws_tests: the socket reads the reply to its request, then is closed with WS_CLOSE_SESSION_REVOKED. Also gates that suite's WS-mutation audit case (with rpc_path; it calls _testing_drain_effects).

true on fuz_app's own spine presets — the TS spine binary mounts its full action set on /api/ws, and the Rust testing_spine_stub serves one action registry on RPC and WS. A MountFlag: a consumer's WS endpoint carries whatever its domain mounts, so it states true once the account actions are there.

type boolean

readonly

cell_gated_create

A test CellCreateAuthorize policy is live-mounted on the backend's cell layer — creating a kind: 'gated' cell requires the participant role or admin; every other kind (and a typeless cell) is open. Gates describe_cell_gated_create_cross_tests, the TS↔Rust cell-creation- authorizer parity proof. The authorizer adds no method / column / wire shape, so schema-snapshot + action-manifest parity are blind to an authorizer divergence — this behavioral cross case is the only gate that catches one. true only on the reference spine binaries that mount the test policy (the TS spine full_spine_mount + the Rust testing_spine_stub); consumers and the in-process default app don't mount it. The same binaries mount the steward-revoke test policy (test_cell_grant_steward_revoke_authorize) beside it, so the flag also gates describe_cell_grant_steward_cross_tests (with cell_relations).

type boolean

readonly

ws_role_gated

The backend mounts a second, role-gated WebSocket endpoint at SPINE_ROLE_GATED_WS_PATH, gated on SPINE_ROLE_GATED_WS_ROLES, beside its ungated ws_path. Gates describe_ws_role_gated_cross_tests: a revoked global grant of a listed role closes the account's gated socket with WS_CLOSE_PERMISSION_REVOKED, its ungated socket stays open and still receives the account's pushes, a re-upgrade is refused at the gate, and a scoped revoke closes nothing. true only on the reference spine binaries that mount that endpoint (the TS spine binary + the Rust testing_spine_stub).

type boolean

readonly

rooms

The room verbs (create_room_actions — room_join, room_leave, room_send, room_state_set, room_watch, room_unwatch) are mounted on the backend's ungated ws_path, over an exclusive room registry on that endpoint's connection registry, with the test room authorizer (test_room_authorize, the twin of the Rust stub's TestRoomAuthorize: the room id's prefix picks the rule), the per-connection room limiter at DEFAULT_ROOM_RATE_LIMIT, and the default registry bounds. Gates describe_rooms_ws_cross_tests. A backend declaring it also mounts _testing_room_evict, which the eviction case drives, and declares it in testing_backdoors, as describe_spine_cross_suites requires. Like cell_gated_create, the authorizer is a test policy, so true only on the reference spine binaries (the TS spine binary + the Rust testing_spine_stub) and on a consumer's test binary that mounts the same; a consumer mounting rooms over its own authorizer states false.

type boolean

readonly

ws_refusal_body

A refused WebSocket upgrade carries its refusal body — the flat {error, ...} the same refusal answers over plain HTTP. Not a gate: it forks how describe_transport_composition_cross_tests reads its WS rows and how describe_cross_process_ws_tests reads its disallowed-origin refusal. true, an empty refusal body fails the case; false, an empty body is allowed (the case pins the status alone) and a non-empty one is still asserted.

false on Node: @hono/node-server writes a refused upgrade to the raw socket with Content-Length: 0, dropping the response body. true on Bun and the Rust spine, which send the response as built.

type boolean

readonly

ws_upgrade_runtime_refusals

The upgrade requests the runtime refuses itself, before the app runs — each a WsUpgradeRuntimeRefusal. Not a gate: the request header wire leg (describe_request_header_conformance_wire_cross_tests) expects that runtime answer, a 400 and no 101, for a row naming a refusal the backend declares, and the table's own answer on every other backend — so the declaration fails the day the runtime stops refusing.

['empty_host'] on Node: @hono/node-server builds an upgrade's URL from the first Host line, and an empty one makes that throw, which it answers with a bodiless 400. [] on Bun and the Rust spine, whose host gate answers the request.

type readonly "empty_host"[]

readonly

runtime_resolves_dot_segments

The backend's runtime resolves dot segments — . and .., literal or percent-encoded (%2e) — before the app sees the request, so the router reads /api/../health as /health. Not a gate: the request target wire leg (describe_request_target_conformance_wire_cross_tests) expects a dot-segment row's expect_where_dot_segments_resolved answer where it is true and the row's raw-path expect where it is false, so the declaration fails the day the runtime changes.

true on Node and Bun, which build the request's URL by the WHATWG URL parser (Bun keeps no raw target at all), and in-process, where the Request does the same; false on the Rust spine, whose router matches the raw path, dot segments kept.

type boolean

readonly

spine_fallback

An unmatched path outside the auth scope is answered by the spine's own fallback — the plain-text 404 Not Found. Gates the request target wire leg's rows that land outside /api (requires), so a backend serving a static or SPA fallback of its own there declares false and keeps the rest of the leg; those rows then show as a skipped test.

true in both families' defaults, on fuz_app's spine presets and in-process.

type boolean

readonly

host_gate

The host gate (DNS rebinding) is on, refusing a Host that is neither loopback nor allowlisted with 403 forbidden_host. Gates the request header wire leg's rows the table expects the host gate to refuse (describe_request_header_conformance_wire_cross_tests), so a backend running with the gate off (host_gate: false on create_app_server) declares false and keeps the rest of the leg; those rows then show as a skipped test.

true in both families' defaults, on fuz_app's spine presets and in-process — the gate is on by default on both spines.

type boolean

readonly

testing_backdoors

The _testing_* backdoors the backend mounts on its RPC endpoint, from TESTING_BACKDOOR_METHODS (a consumer's own seams stay off it). Not a flag, but declared like a MountFlag: no family default, so every config states it. describe_testing_backdoor_cross_tests checks the declaration against the backend — a declared method must be mounted, an undeclared one must answer method_not_found — and runs its credential-gate rows over the declared ones; describe_spine_cross_suites requires _testing_reset and _testing_drain_effects (the per-test reset and the audit barrier), skips a suite whose backdoor is undeclared, naming it — credential_conformance (_testing_credential_read), credential_deadline (_testing_shorten_credential_expiry), origin_conformance (_testing_origin_check), ws_outbound_overflow (_testing_flood_notifications) — and requires _testing_put_fact of a backend declaring fact_serving and _testing_room_evict of one declaring rooms. default_cross_process_setup requires _testing_db_invariants, its per-test invariant check, unless the setup turns the check off (exclude_db_invariants: {all: reason}).

fuz_app's spine presets declare every one; the in-process transport none (the backdoor suites are cross-process only).

type readonly TestingBackdoorMethod[]

readonly

BackendCapabilities import {in_process_capabilities} from '@fuzdev/fuz_app/testing/cross_backend/capabilities.js';

Capability declarations for the in-process Hono transport. Nearly every flag is true because in-process testing exercises the full backend with no missing optional behaviors. The exceptions are the flags whose cases are cross-process-only: peer_request (describe_peer_ping_ws_tests needs a real bound socket with an on_request responder via create_ws_transport, so the in-process driver never runs it — the transport itself supports server-initiated requests), ws_handshake_pipelining (raw bytes on a real socket), ws_account_actions (a real socket's reply-then-close ordering), cell_gated_create, ws_role_gated, and rooms. Cross-process consumers declare each flag explicitly per backend.

The capabilities that describe a backend's own mounts, never a runtime trait: what a consumer chooses to serve. They have no family default — state each flag in your backend config's capabilities; a missing one would silently skip its suites, so leaving one out is a type error.

Pick keeps the list honest: a name that is not a BackendCapabilities flag fails to compile.
