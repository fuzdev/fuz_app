testing/cross_backend/db_state_diff.ts

The database a test leaves, read directly and normalized, so two backends driven through the same requests can be compared row for row.

The differentials compare answers. A write one backend makes and the other doesn't — an audit field, a metadata key, a row inserted and rolled back — reaches no answer unless some test reads it back, so it is invisible there. create_db_state_probe reads a backend's database over its own connection (the backend must be on PostgreSQL the test process reaches), after draining the backend's in-flight detached writes (audit rows; on the Rust spine also the token touch and the bootstrap write), and normalize_db_state maps the rows onto a form both backends share when they wrote the same things:

Every table of the public schema is read (schema_version aside), its columns and their types from query_schema_snapshot, so a new table or column joins with no edit here, under the rules its type takes:

  • Ids become positional placeholders (<id:1>, <tok:1>), numbered by a canonical walk: the tables in DB_STATE_TABLES order, then any other in name order; each table's rows sorted by its DB_STATE_SORT_KEYS columns (accounts by username, actors by account and name, audit rows by seq), then by the whole row with no unnumbered id; each row's columns and every JSON object's keys sorted. So a reference — a column or a UUID inside metadata naming another row — compares, while the values themselves differ per backend.
  • Secrets and digests — API tokens, bare 64-hex digests (a session's id, a token's hash) — become constants (<token>, <hash>): they are fresh per backend and nothing compares them. Sessions and tokens, sorted by account then content, compare as a multiset per account. A password_hash keeps its argon2 parameter prefix ($argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>), so the cost parameters compare and the salted digest doesn't. A blake3: content address and a bytea (hex) are compared as they are.
  • Generated usernames (GENERATED_USERNAME_PATTERN) become positional placeholders like ids; a username a test names stays as it is.
  • Timestamps — a timestamp column's value, and a second-precision ISO string inside a JSON value — become their dense rank among every timestamp in the dump (<t:3>); null stays null. Two writes in one transaction share a rank, a later write ranks after, and a backend setting a column the other leaves null differs.
  • A token's last use — api_token.last_used_at — becomes <set> or stays null, and joins no rank: the touch is a detached write that runs concurrently with its own request's transaction on both spines, so its order against that request's writes is promised by neither, and ranking it would shift every later rank. last_used_ip compares as it is.
  • Expiries — a column or JSON key named expires_at, in a row with a created_at — become their offset from that created_at, rounded to the minute (+30d0h0m), and join no rank: a rank keeps order and loses the duration, so a lifetime cut from 30 days to 7 would rank the same.
  • seq becomes the offset from the dump's smallest, and the dump carries audit_seq_advance: how far the audit sequence moved between mark and the read, so an audit insert that rolled back — no row left, a sequence value spent — differs too. Rows of successive requests take seq in request order because fuz_app's two test binaries (the TS spine binary and testing_spine_stub) settle an HTTP answer's writes before answering (await_pending_effects: true on TS, the stub's await_background_writes_layer); in production a refusal's row is written after its answer, and the next request's row can land first.

diff_db_states lists every place two normalized states differ, as DifferentialDiffs under db. (db.audit_log[2].metadata.reason, db.audit_seq_advance), the paths a known-divergence ledger names.

Rows compare by position after the sort, so a row one backend writes and the other doesn't shifts every later row of its table. Rows the sort can't tell apart but for an id are ordered by that id's raw value, which differs per backend; they then normalize equal unless something else references them.
