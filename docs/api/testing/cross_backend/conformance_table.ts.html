testing/cross_backend/conformance_table.ts

Table runner for the declarative cross-backend conformance suite.

describe_conformance_table_tests takes a list of ConformanceCase rows plus the standard {setup_test, surface_source, capabilities} fixture protocol every Tier 1 suite uses — so one runner drives both transports: in-process via default_in_process_setup (fast, every gro test) and cross-process via default_cross_process_setup (the conformance gate, exercising each impl's real auth resolution over real HTTP). Same case definition, transport-parameterized.

Each row references a method; the runner resolves its input / output schema from the live spec registry (RPC) or RouteSpec (the 6 REST auth routes) — the row never carries a schema. The principal the row runs as resolves to a TestFixture accessor via resolve_conformance_principal — no inline credential minting.

Every response also passes an always-on no-fingerprint invariant (assert_no_fingerprint_headers over FINGERPRINT_HEADERS — Server / X-Powered-By / WWW-Authenticate must stay absent on both spines), and a row may pin further header expectations via expect.headers. Headers are deliberately kept out of the equivalence-group {status, body} comparison.

On HTTP every response is also held to what it does to the session cookie: the row's expect.set_cookie — omitted meaning none — is matched against classify_session_cookie_effect of its Set-Cookie lines, which reads the clear and the mint through the spine's own formatters, with a floor behind it that no response outside 2xx mints one (assert_session_cookie). An RPC error row is held to its JSON-RPC error.code too, not just the status it answers. Rows that can't honestly run are refused at collection (check_conformance_cases).

Given ws, the runner sends each case as a frame on a WebSocket instead: the principal opens an admitted socket and the frame meets the per-message gates. The frame carries the same JSON-RPC envelope the HTTP body does, so the same rows hold, read through the status the HTTP binding maps the frame's error code to; the cases a socket can't carry are left out (is_ws_conformance_case).

A case binding request.acting gets params.acting filled with a real actor id at run time (ConformanceActingBinding), so rows can act as a named actor of a multi-actor keeper without knowing its id.

A case's RPC method resolves from the declared rpc_endpoints first, then from live_rpc_endpoints when given — the methods a backend live-mounts off the declared surface (cell verbs, opt-in resolvers, _testing_* backdoors), so rows can reach them too.

(sent: Pick<ConformanceCaseResponse, "status" | "set_cookies">, c: ConformanceCase, cookie_name: string): void import {assert_session_cookie} from '@fuzdev/fuz_app/testing/cross_backend/conformance_table.js';

Assert a response's session cookie lines against the row's expect.set_cookie (omitted, 'none'), by the classification both the runner and the differential read (classify_session_cookie_effect) — the assertion that decides a row.

Ahead of it runs the floor: a response that is not 2xx mints no session cookie (find_session_cookie_mints, which reads a mint in any shape). It is a backstop, not a second guarantee: check_conformance_cases refuses a non-2xx row expecting a mint, so on a row the table collected, a refusal that mints already fails the effect assertion. The floor names the cause plainly when it does, and holds for a caller asserting a row the collection never saw.

Refuse the rows a table can't honestly run, before any is sent, each throw naming the case:

  • a REST row pinning error_reason: null — a REST error body always names its code in error, so the row pins that code instead;
  • a REST row setting error_code, which only a JSON-RPC envelope carries;
  • a row whose status is not 2xx expecting the session cookie minted (set_cookie 'set' or 'clear_then_set') — no refusal may mint one, so the row contradicts the floor assert_session_cookie holds every response to.

ConformanceCaseResponse

ConformanceCaseResponse import type {ConformanceCaseResponse} from '@fuzdev/fuz_app/testing/cross_backend/conformance_table.js';

One case's request as sent and its response unparsed: the HTTP status, the response-headers snapshot (lowercased keys), every Set-Cookie line in order (the snapshot keeps only one), and the JSON body exactly as the server sent it — the whole JSON-RPC envelope for an RPC method, undefined for a REST body that is not JSON.

Over a WebSocket the body is the response frame, the headers and Set-Cookie lines are empty (a frame carries none), and the status is the one the HTTP binding answers for the frame's outcome: 200 for a result, else jsonrpc_error_code_to_http_status of its error code — so a row's expect.status reads as the error code on both transports.

#

testing/cross_backend/conformance_table.ts view source

readonly string[] import {FINGERPRINT_HEADERS} from '@fuzdev/fuz_app/testing/cross_backend/conformance_table.js';

Response headers that fingerprint the backend implementation or framework. Neither spine emits these; the runner asserts they stay absent on EVERY conformance response so a framework upgrade or consumer middleware that adds (say) Server: to one spine can't silently become a backend-identifying oracle. Lowercased — matched against the lowercased-key snapshot headers_to_record produces.
