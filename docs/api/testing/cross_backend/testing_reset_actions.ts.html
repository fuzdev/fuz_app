testing/cross_backend/testing_reset_actions.ts

Test-binary RPC actions for cross-process integration tests.

The daemon-token-authed actions bundled by create_testing_actions: _testing_reset (DB wipe + keeper re-seed), _testing_drain_effects (effects barrier), _testing_mint_session (forge an expired-by-construction server-side session on any account, a dead session no wire path leaves — the database-invariant twin check's session on a deleted account), _testing_put_fact (seed an embedded fact for the fact-serving suite), _testing_schema_snapshot (introspect the live schema for cross-impl parity diffing against a Rust backend's fuz_db snapshot), _testing_migration_tracker (dump the schema_version tracker rows for cross-impl migration-identity parity — the provenance half the snapshot gate excludes by design), _testing_db_invariants (run the database invariant statement for the per-test check), and _testing_flood_notifications (queue a burst of notifications onto the caller's own WebSocket connection, to push its outbound queue past its byte budget).

Two further daemon-token actions live here but are not bundled by create_testing_actions, and are appended at the full-mount layer (build_full_spine_rpc_actions) instead: _testing_action_manifest (dump the live RPC registry for cross-impl method-set + auth-shape parity — it must enumerate *every* mounted method, so it goes where the complete list exists) and _testing_shorten_credential_expiry (pull an account's credential expiries in to seconds from now, shorten-only, for the credential-deadline cases) — the latter kept out of the bundle so a consumer whose Rust binary doesn't mount its mirror keeps a green manifest gate. _testing_origin_check, mounted the same way, lives in the hono-free testing_origin_check.ts.

_testing_reset — full DB wipe + keeper re-seed + optional secondary-account seeding. The handler first fires the consumer-supplied domain-state callback (domain rows depend on auth rows, so a domain table with a restricting FK to actor empties before the rows it references go), then wipes every auth-namespace row (no keeper-preserve filter), flips bootstrap_lock back to its post-bootstrap shape, seeds a fresh keeper account inline (reusing create_test_account_with_credentials so cross-process matches in-process write semantics), queues the daemon-token cache refresh to point at the new keeper once the reset commits, and seeds any caller-requested extra_accounts (also direct-inserted at this setup step). The new keeper + secondary credentials return as the action output so the per-test fixture closes over them.

In-process and cross-process keeper lifetimes match: both modes run against a freshly bootstrapped keeper per test, so mutation-cascade tests (password change, revoke-all, hardcoded-username signup uniqueness) and direct keeper-vs-admin probes work uniformly cross-process.

Keeper ≠ admin. The keeper and admin roles are independent. Keeper authorizes daemon-token / bootstrap paths; admin authorizes the user-facing admin RPC surface. _testing_reset seeds the keeper account with [ROLE_KEEPER, ROLE_ADMIN] by default — matching the production bootstrap_account flow — plus any roles passed via extra_keeper_roles. Tests probing the keeper-vs-admin separation (a keeper-only account must 403 on admin RPCs) declare a secondary via extra_accounts: [{username, roles: [ROLE_KEEPER]}] so the account is seeded at this same bootstrap-equivalent step.

No free-form runtime bypass. There is no action for arbitrary direct role grants: a runtime bypass would let tests skip the production consent flow's side-effects (audit emit, WS fan-out) and silently mask bugs in those paths. The bypass that does exist — extra_accounts — is framed as bootstrap-time seeding, the same shape bootstrap_account itself uses to grant the initial KEEPER + ADMIN pair. Tests that want a role on a *post-bootstrap* account must route through role_grant_offer_create + role_grant_offer_accept (the production path); they observe the full event chain.

Production safety: this module lives under cross_backend/ and starts with import '../assert_dev_env.ts'; — production bundles either tree-shake the module out or throw at startup. The Rust mirror (fuz_testing crate) ships a parallel action; `cargo xtask check-release blocks fuz_testing` from entering production dep graphs.

_testing_drain_effects — await in-flight fire-and-forget work so a following audit_log_list or database read is authoritative. The deterministic barrier the cross-backend conformance suite uses in place of a poll/sleep before asserting on audit rows.

The handler waits, repeating until both are empty, for the effect flushes on AppDeps.request_tracker (RequestTracker.drain_flushes: each request's eager pending_effects — the bearer leg's token touch among them — and its post-commit thunks) and for the pool writes of AppDeps.audit (AuditEmitter.drain_inflight) — a thunk can start an audit write, and a write's listener fan-out runs in a thunk. It matters whatever the transport: both test binaries settle an HTTP answer's effects before it responds (the TS binary through await_pending_effects: true, the Rust stub through its await_background_writes_layer), but a WS mutation is answered before its effects flush (reply-then-close for a self-revocation), so its audit write or post-commit effect can still be running when the caller reads the reply. The Rust spine awaits the same work on its one tracker, BackgroundWrites.

Covered: every flush and emit that started before the drain was dispatched, and any started while it waits. Not a handler still running — the drain's own request is one, and its flush starts only after it answers — nor work that starts after the drain resolves.

{ readonly method: "_testing_flood_notifications"; readonly kind: "request_response"; readonly initiator: "frontend"; readonly auth: { readonly account: "required"; readonly actor: "none"; readonly credential_types: readonly [...]; }; ... 5 more ...; readonly description: string; } import {testing_flood_notifications_action_spec} from '@fuzdev/fuz_app/testing/cross_backend/testing_reset_actions.js';

_testing_flood_notifications — queue a burst of notifications onto the caller's own WebSocket connection, all in one synchronous run, so a suite driving the server from outside can push a connection's outbound queue past its byte budget deterministically — without a second producer, and whether or not its client is reading: the connection's write pump gets no turn while the handler runs, so the burst waits at once. Past the budget the server closes the socket with WS_CLOSE_OUTBOUND_OVERFLOW.

Each notification is {"jsonrpc":"2.0","method":"_testing_flood","params":{"index":<i>,"payload":"<size × 'x'>"}} with index counting from 0, so every frame is a little longer than size bytes and a client can tell which frames reached it.

The result is {queued: count} — the number asked for, not the number that fit: when the burst overflows the queue the connection is closed and this response is never written. A burst that fits arrives in order, ahead of the response.

A call past TESTING_FLOOD_MAX_COUNT, TESTING_FLOOD_MAX_SIZE, or TESTING_FLOOD_MAX_TOTAL_BYTES (count × size) is refused with invalid_params and queues nothing. Over HTTP there is no connection to queue onto, so the call is refused with invalid_params, reason ERROR_TESTING_FLOOD_NO_CONNECTION, rather than answering as though it had flooded something.

_testing_mint_session — mint an expired-by-construction server-side session for an existing account and return its signed cookie value.

expires_in_seconds is constrained negative (a safe integer at most -1) so the action is structurally incapable of minting a *usable* session: it can only produce an already-backdated, already-dead auth_session row. The daemon-token gate + loopback binding already fence the backdoor, but the negative constraint is the make-impossible-states floor — even a misuse can't forge a valid session for an arbitrary account_id. The Rust mirror (fuz_testing::create_testing_mint_session_action_spec) enforces the same floor.

The minted auth_session row's expires_at is backdated while the returned cookie's own signed payload stays valid (future). Cross-process auth resolution therefore passes the cookie-payload gate (parse_session_from_cookies) and is refused by the authoritative DB-row gate (query_session_get_valid — WHERE expires_at > NOW()) — the gate the in-process payload-expiry tests never reach. It forges a dead session no wire path leaves (the database-invariant twin check's session on a deleted account); a session that lived and then expired is the expired_session principal's, over _testing_shorten_credential_expiry.

auth gates on the daemon-token credential, matching _testing_reset — effectively keeper-only. Like its siblings the action is internally privileged (a direct auth_session insert the production wire never exposes); daemon-token auth is the structural fence and the module's assert_dev_env import (TS) plus the Rust cargo xtask check-release dep-graph audit keep the _testing_ surface out of every shipped build.

Input:

_testing_schema_snapshot — introspect the live database into a normalized SchemaSnapshot for cross-impl parity diffing. The cross-backend harness calls this on each backend, then assert_schema_snapshots_equals the results (a Rust backend answers from fuz_db::query_schema_snapshot; the shapes match by design). Optional exclude_tables drops documented divergences from both sides before comparison.

A backend running on pglet (a TS backend config's memory:// default) answers with an error when its schema holds an index: the snapshot exists to be compared, and pglet's index definitions omit the modifiers a comparison needs (query_schema_snapshot). Run the backend on PostgreSQL.

_testing_shorten_credential_expiry — pull the expiry of an account's stored credentials (every auth_session and api_token row it owns) in to seconds from now, so the cross-backend credential-deadline suite can open a WebSocket or audit stream on a credential that expires a moment later and watch it close at the deadline (ResolvedAuth.credential_deadline) without waiting out a real lifetime.

Applied before the open: it rewrites the stored rows, and a connection reads its deadline when its credential resolves, so only one opened afterwards sees the near deadline.

Shorten-only. The new expiry is LEAST(expires_at, NOW() + seconds) — an eternal token gains one, and nothing already due sooner moves later, so the action can neither extend a credential's life nor revive an expired one; seconds is an integer from TESTING_SHORTEN_CREDENTIAL_EXPIRY_MIN_SECONDS to TESTING_SHORTEN_CREDENTIAL_EXPIRY_MAX_SECONDS. The Rust mirror is fuz_testing::create_testing_shorten_credential_expiry_action_spec.

Like _testing_origin_check, it is not bundled by create_testing_actions: a consumer whose Rust binary doesn't mount the mirror would fail its action-manifest parity gate. The spine test binary appends it at the full-mount layer (build_full_spine_rpc_actions).
