testing/test_app.ts

Fully assembled Hono test app for integration tests.

create_test_app combines create_test_app_server (testing/app_server.ts, the vitest-free backend primitives) with create_app_server, and hands back the app, the backend, the surface, and request header builders. Built inside a test (its body or a beforeEach), the app's database is held to the auth-schema invariants when the test finishes, and the app is closed then, failing the test on a close that gave up on work still in flight.

(options: CreateTestAppOptions): Promise<TestApp> import {create_test_app} from '@fuzdev/fuz_app/testing/test_app.js';

Create a fully assembled test app with a Hono server, middleware, and routes.

Combines create_test_app_server + create_app_server into a single call. Disables every rate limiter (rate_limiters: 'disabled_for_testing') and logging by default (test-friendly). A limiter passed through app_options wins over the mode, so a rate-limit test enables just the one it pins.

A fresh Hono app is created each call — middleware closures bind to the server's deps (db, keyring), so reuse across servers is unsafe. The expensive resource (the WASM database) is cached separately in testing/db.ts.

Built inside a running test (its body or a beforeEach), it registers one hook for when the test finishes: the database invariant check (skipped when the test already failed, as register_db_invariants_check does), then the close. The close throws when it gave up on work still in flight, unless the test failed or closed the app itself (cleanup, or server.close(), whose outcome is the test's). So an app built in a test lives only for that test. Built in beforeAll, nothing is registered: the suite closes the app, and calls check_db_invariants_after_all(() => test_app), or, when the describe closes the app in its own afterAll, `check_db_invariants_after_suite(suite, test_app)` inside that hook ahead of the close.

login_ip_rate_limiter?

Per-IP rate limiter for login + password change — the distributed-spray backstop. Omit or undefined to use a default limiter (5 attempts per 15 minutes) under rate_limiters: 'enforced', none under 'disabled_for_testing'. Pass null to explicitly disable rate limiting. Also available on AppServerContext for route factory callbacks.

One instance per auth surface, not one shared across all four. These buckets are monotone within their window — a success never refunds them (see RateLimiter.reset) — so a shared instance let a failure on any surface spend the budget that bounds guessing on every other one, and let one caller's exhaustion deny four routes at once. Pass the same limiter to two of these fields to opt back into a shared budget.

auth_cleanup?

Whether the auth cleanup runs beside the server — required, with no default, so a server neither gets nor loses the sweeps without writing it out. {every_ms} runs start_auth_cleanup over backend.deps — a pass as assembly finishes, then one per every_ms — stopped by AppServer.close within its drain bound. Each pass deletes expired sessions and closes the connections they opened through deps.connection_closer (every WebSocket connection registry and audit stream this server mounts), and audits each newly expired role_grant offer once.

A production server passes {every_ms: DEFAULT_AUTH_CLEANUP_INTERVAL_MS}. With 'off' nothing sweeps: expired session rows accumulate and an offer's expiry is never audited. Connections do not depend on it — each closes at its credential's deadline (auth/credential_deadline.ts), and the sweep's close repeats that one. Twin of the Rust spine's AuthCleanupSchedule::Every, which a server's backend options carry and its backend attaches as a fuz_auth::AuthCleanup.

'off' in an in-process test harness — a background pass deletes rows and writes audit rows mid-test — and in a process that runs run_auth_cleanup on a schedule of its own.

Checked with the other options, before assembly acquires anything: every_ms must be a positive finite number of ms no greater than PERIODIC_INTERVAL_MS_MAX.

type AuthCleanupSchedule

upgrade_websocket?

The Hono runtime adapter's upgradeWebSocket helper, which services every mounted ws_endpoints entry. Required when ws_endpoints resolves non-empty — assembly throws without it — and unused otherwise.

Bun's is upgradeWebSocket from @hono/bun, whose websocket goes to Bun.serve. Node's is upgradeWebSocket from @hono/node-server, which upgrades only on a server given a ws WebSocketServer built with noServer: true; cap its maxPayload near the endpoint's max_message_bytes, since ws defaults to 100 MiB:

import {serve, upgradeWebSocket} from '@hono/node-server'; import {WebSocketServer} from 'ws'; const server = await create_app_server({..., upgrade_websocket: upgradeWebSocket}); const wss = new WebSocketServer({noServer: true, maxPayload: 2 * max_message_bytes}); serve({fetch: server.app.fetch, port, websocket: {server: wss}});

Test harnesses pass stub.upgradeWebSocket with create_stub_upgrade from testing/ws_round_trip.ts.

type UpgradeWebSocket<unknown, any, WSEvents<unknown>>

ws_endpoints?

WebSocket endpoint specs — single source of truth for both surface generation *and* live dispatch. Each entry is auto-mounted via register_action_ws against the assembled Hono app on every runtime, so consumers don't call register_action_ws themselves.

An entry that omits actions serves the actions of the sole rpc_endpoints entry (to_ws_actions: the protocol actions first, then the RPC set), so one action set runs on both transports; assembly throws unless exactly one RPC endpoint resolves.

Accepts either an array (evaluated eagerly) or a factory (ctx: AppServerContext) => ReadonlyArray<WsEndpointSpec> (evaluated after the server context is assembled). Use the factory form when action lists depend on ctx.deps — e.g. when spreading create_standard_rpc_actions(ctx.deps) over WS.

When non-empty, upgrade_websocket must be supplied (throws otherwise). A factory returning [] does NOT trip the check — feature-flag gated WS surfaces stay safe.

Every mount gets what the HTTP surface gets: the auth middleware (a path outside AUTH_MIDDLEWARE_PATH throws at assembly, like rpc_endpoints), the server's allowed_origins unless the spec narrows them (a spec's own list gets the same wildcard check, allow_origin_wildcards), and the same action_ip_rate_limiter / action_account_rate_limiter instances the RPC endpoints charge — one budget per action across both transports. The upgrade routes register after the route specs and before post_route_middleware and static_serving, so neither runs ahead of an upgrade.

Duplicate path values across two WsEndpointSpecs, and a path a GET RouteSpec already claims, throw at assembly before any endpoint mounts (Hono would silently shadow them otherwise).

Every mounted connection registry is added to deps.connection_closer, so the revocation handlers' post-commit closes reach its sockets, and so does the one revocation guard create_app_server registers on that closer (create_revocation_guard) when it mounts a WS endpoint or the audit stream. Each is added to deps.notification_sender too, so a notification any action handler sends — over HTTP RPC or a socket — reaches the account's sockets on every mounted registry, once per registry however many endpoints share it. AppServer.close removes both memberships again.

type readonly WsEndpointSpec[] | ((context: AppServerContext) => readonly WsEndpointSpec[])
