assert_response_matches_spec
#

testing/integration_helpers.ts view source

(route_specs: RouteSpec[], method: string, path: string, response: Response, route_error_maps?: ReadonlyMap<string, RouteErrorMap> | null | undefined): Promise<...> import {assert_response_matches_spec} from '@fuzdev/fuz_app/testing/integration_helpers.js';

Validate a response body against the route spec's declared schemas.

For 2xx responses, validates against spec.output. For an error response (400 and up), checks it against the route's error map (resolve_route_error_map) — the one in route_error_maps, an AppSurfaceSpec's, built with the app's middleware, or without one the route's own — through assert_error_response_declared, by the rule the DEV error check runs (check_route_error): the status must be declared and the body must parse against it. A 500 internal_error and a 503 service_unavailable are always accepted, and on a jsonrpc route (the RPC endpoint's) a JSON-RPC error envelope is not a REST error body; on any other route it is checked like any error body.

The route is the one find_route_spec finds, the request's as Hono dispatches it. A failure reads as the DEV check logs it (format_route_error_check), then : and the issues or the body as JSON.

Only a JSON response, by its Content-Type (is_json_response, the DEV check's gate), has a body to check. A non-JSON response passes only where no schema applies: a 2xx on a route with a null output, or an error status the map doesn't declare.

An answer no route gave never passes, whatever the route declares: a 405, the JSON route_not_found 404, or the plain NOT_FOUND_TEXT 404 (server/unmatched_route.ts) means the backend doesn't mount the route the spec describes.

Find the route spec a request reaches: the first in list (mount) order whose method and path template match it, HEAD read as GET — the order Hono dispatches by, which the DEV error check reads through Hono's own router (create_route_lookup). A path template passed as the path (/api/things/:id, a segment that is * or starts with :) finds its own spec first, outranking mount order.

round_trip_uses_fresh_account
#

testing/integration_helpers.ts view source

(principal: AuthPrincipal, side_effects: boolean): boolean import {round_trip_uses_fresh_account} from '@fuzdev/fuz_app/testing/integration_helpers.js';

Whether a round-trip sends a request as a fresh account rather than the shared authed one: a side-effecting request picked for the 'authed' principal. Generated input omits optional fields, and an omitted target on a self-service action is the caller — account_delete deletes it, account_session_revoke_all, a logout or a password change end its session — so any side-effecting call may destroy the credential it was sent with, and on a shared account every later call would refuse as unauthenticated. Keyed on the request's own side-effect signal (an action's side_effects, a route's non-GET method) rather than a list of known destroyers, so a consumer's self-targeting action is covered without registering it. The other principals stay shared: the keeper and its daemon token are one per fixture, and an admin-gated request with generated nil ids targets no existing account. A credential they lose still fails the round-trip on its 401 check (is_unauthenticated_refusal).

to_principal_transport
#

testing/integration_helpers.ts view source

(principal: AuthPrincipal, fixture: PrincipalTransports): RpcTestTransport import {to_principal_transport} from '@fuzdev/fuz_app/testing/integration_helpers.js';

The transport a principal's request goes through, so the request carries the principal's credential and nothing else. Cross-process fixture.transport adds the keeper's session cookie from its jar (unless the request names a Cookie) and a default Origin:

  • 'daemon_token' goes cookie-free and without an Origin. Behind an Origin the daemon token is discarded as browser context and the keeper's cookie answers in its place, so a daemon-gated call is refused for its credential type and its success path goes unexercised.
  • 'public' goes cookie-free with the default Origin kept, so a public route or method is called anonymously on both legs — over fixture.transport the keeper's cookie would ride along cross-process while in-process the call is anonymous.
  • 'admin', 'keeper' and 'authed' keep the fixture's transport: each sends a session Cookie header (to_principal_headers), which replaces the jar's.
