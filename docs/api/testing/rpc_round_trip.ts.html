testing/rpc_round_trip.ts

Schema-driven round-trip validation for RPC endpoints.

For every RPC method, generates valid params and fires JSON-RPC requests (POST for all methods, GET for reads), validating that responses are well-formed JSON-RPC. Successful responses are validated against the method's declared output schema. DB-backed via the suite's setup_test fixture-producing callback.

Cadence: per-describe setup_test() call (see testing/round_trip.ts module docstring). The generic POST and GET cases fire one JSON-RPC envelope per method-direction against shared principals (an authed account, an admin account, the keeper). A side-effecting method called as the authed account runs on a fresh account of its own (round_trip_uses_fresh_account): the generated params of a self-targeting method act on the caller — an account_delete with no account_id deletes it, an account_session_revoke_all ends its session — and on the shared account that would leave every later call refused as unauthenticated. A 401 to any non-public call fails (assert_rpc_authenticated), so a credential lost some other way goes red rather than vacuous. The success_fixtures case also mutates — each fixture builds a row and the call revokes, deletes, or decides it — so it runs last on the describe's fixture, and each factory seeds its own rows.

Guard against a refusal that says the call carried no valid credential when it carried one (is_unauthenticated_refusal). The round-trip sends every non-public method a live credential its auth admits, so such a 401 means the backend failed to authenticate it — most often because an earlier call destroyed it (a self-delete, a revoke-all), which would turn every later method's coverage into a vacuous refusal. A public method may still answer 401 (a login with a wrong password), and so may a handler refusing an authenticated call with a reason of its own (invalid_credentials).

Run schema-driven round-trip validation for RPC endpoints.

For each method:

  1. Generate valid params from the action's input schema
  2. Fire a POST request with JSON-RPC envelope
  3. For side_effects: false methods, also fire a GET request
  4. Validate response is well-formed JSON-RPC; successful responses are also validated against the method's declared output schema

Error responses (from missing DB state, etc.) are expected and validated as well-formed JSON-RPC errors. Successful responses are validated against action.spec.output. Two error classes fail loud instead of passing as a valid envelope: method not found (-32601) means the backend is missing a method the local surface advertises (assert_method_implemented), and a crash — HTTP 500, internal_error (-32603), or a ≥500 with no JSON-RPC envelope — means the backend failed on schema-valid input (assert_not_crash). A declared ≥500 code (service_unavailable, timeout) passes as a refusal. A method the suite can't drive generically goes in skip_methods; one whose generated params can't reach its handler gets an input_overrides entry.

success_fixtures?

Success-case fixtures for methods whose populated success body the generic nil-id input can't reach — referential reads (*_get, *_log) whose required ids must point at existing rows. Maps method name to an async factory that receives the per-test fixture (so it can seed the referenced state — e.g. create a repo via fixture.transport + fixture.create_session_headers()) and returns the params that drive a success response.

Distinct from input_overrides, which only swaps the request params; the response may still be a valid *error* envelope (missing-row not_found), which the generic loop accepts. A success_fixtures entry asserts the response is ok and validates result against the method's output schema — so a backend that drops a field, or errors where the other backend succeeds, fails loud. This is the success-shape parity check the nil-id round-trip structurally cannot perform (it only ever sees error envelopes for referential methods).

Fired as POST. The factory runs against the shared per-describe fixture, so it must not assume a clean slate between entries (seed unique state). By default the request carries the identity the generic loop picks for the method's auth (authed / admin / keeper); a case that returns headers sends those instead — for methods whose row must belong to the caller (revoking one's own token or session, retracting one's own offer). create_spine_rpc_success_fixtures (cross_backend/rpc_success_fixtures.ts) builds the map for the standard spine methods.
