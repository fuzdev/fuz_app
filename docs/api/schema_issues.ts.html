schema_issues.ts

Validation issues from either schema library the stack's specs use: Zod (z.core.$ZodIssue) and @fuzdev/fuz_schema (SchemaIssue). A schema is wholly one library, so one parse's issues are all of one kind; these helpers read either, so the dispatcher, ActionEvent and the forward-compatible reads treat a spec the same whichever library it is written in, and an error response carries either library's issues in one shape, WireIssue.

issue_is_on_input
#

schema_issues.ts view source

(issue: AnyIssue): boolean import {issue_is_on_input} from '@fuzdev/fuz_app/schema_issues.js';

Whether issue sits on the input itself rather than on one of its fields: a non-object input, or an unknown key on the input object — what the Rust twin refuses before reading any field.

Zod reports both at an empty path, its unrecognized_keys naming the keys. fuz_schema reports a non-object at an empty path and each unknown key as an unknown_key issue whose path ends at the key, so one on the input has a path of the key alone. An unknown key on a nested object is on that field, as Zod's is.

On the wire the unknown_key rule changes no answer today: a root unknown_key comes from a root object, which resolve_issues_invalid_reason already answers with none from its check of the input's keys, or from a schema such as a variant whose fields resolve no reason. It is kept as the direct statement of Zod's rule.

to_wire_issues
#

schema_issues.ts view source

(issues: readonly AnyIssue[], input: unknown): { [x: string]: unknown; kind: string; path: (string | number)[]; expected: string; received: string; message: string; }[] import {to_wire_issues} from '@fuzdev/fuz_app/schema_issues.js';

A failed parse's issues as WireIssues, whichever library made them.

A fuz_schema issue keeps its kind, path, expected and received, and its message is format_issue's text, the path included.

A Zod issue maps to the kind fuz_schema reports for the same check, its message Zod's own text, which names no path:

  • invalid_type — the type's kind (string, number, boolean, bigint, object, record, array); int is integer, a tuple an array, null, undefined, void and nan a literal of the value, nonoptional a missing_key, and a type fuz_schema has no kind for (date, map, set, file, symbol, function, never) a check expecting the type's name. A missing key is reported as fuz_schema reports it, as the type expected with received: 'undefined'.
  • too_small / too_big — min_length / max_length for a string, array, set or file (length >= N), min_value / max_value otherwise (>= N); an exclusive bound writes > or <, which fuz_schema has no check for, and an exact length is reported as the bound it broke.
  • invalid_format — uuid for a uuid or guid, iso_datetime for a datetime, regex for a regex (expecting its pattern), and a check expecting the format's name for every other format.
  • unrecognized_keys — an unknown_key per key, the key appended to the path, as fuz_schema reports them.
  • invalid_union — a variant expecting the options when Zod names a discriminator, else a union expecting each option as fuz_schema names it: by the type or the values it expected of the value, or by the value's type when the option took the type and failed a refinement or a field below. A union refused because more than one option matched is a union expecting exactly one option.
  • invalid_value — a literal of one value, a one_of of more.
  • custom — a check; not_multiple_of a check expecting multiple of N; invalid_key and invalid_element a check expecting a valid key / a valid element.

A Zod issue holds no value, so received is read from input at the issue's path: 'undefined' where a key is missing or the path leads through something that isn't an object. Where an earlier step of a Zod pipe replaced the value, it names the input's value, not the replacement.
