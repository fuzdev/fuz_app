rate_limiter.ts

In-memory sliding window rate limiter.

Tracks failed attempts per key (typically IP address) using a sliding time window. No external dependencies — state resets on server restart.

Reserve, then settle. A handler that checks the limiter, awaits work, and records afterwards lets every request of a concurrent burst pass the check before any of them records — a burst of any size gets through. RateLimiter.try_reserve closes that: it admits a request and counts it in flight in one synchronous step, and the attempt counts against the cap until its RateLimitReservation is settled — record keeps it as an attempt, release gives it back. Every handler whose outcome decides whether the attempt counts reserves, and releases in a finally so an early return or a throw never leaks an in-flight slot; check + record stays for callers that record in the same synchronous step they check.

Attempts count while in flight, whatever their outcome — so a burst of *correct* concurrent attempts from one key is capped too. The password surfaces therefore reserve with RateLimiter.reserve, which waits up to RESERVATION_WAIT_MAX_MS for a slot when the cap is reached only by attempts in flight, and refuses at once when it is reached by recorded ones.

RateLimiter
#

rate_limiter.ts view source

import {RateLimiter} from '@fuzdev/fuz_app/rate_limiter.js';

In-memory sliding window rate limiter.

Stores an array of timestamps per key, plus a count of attempts reserved (try_reserve) and not yet settled. On check/record, timestamps outside the window are pruned. retry_after reports seconds until the oldest active timestamp expires.

The backing store is an LruMap when options.max_keys is a positive number (default DEFAULT_RATE_LIMITER_MAX_KEYS) and a plain Map when max_keys is null. The LruMap path bounds memory under key-enumeration attack at the cost of a slight per-op overhead and the LRU trade-off described on RateLimiterOptions.max_keys.

Parameters that accept RateLimiter | null (e.g. login_ip_rate_limiter, login_account_rate_limiter) disable rate limiting when null is passed — no checks are performed and all requests are allowed through. create_app_server surfaces each disabled limiter as a warning diagnostic.

check

Check whether key is allowed without recording an attempt, counting recorded attempts and reserved ones still in flight.

Prunes timestamps that fell outside the window as a side effect (and removes the key entirely when none remain and none are in flight), so the backing map stays bounded even under read-only traffic.

A check followed by an awaited operation and then a record lets a concurrent burst past the cap; reserve with try_reserve instead.

try_reserve

Admit an attempt for key and count it in flight, in one synchronous step.

The attempt counts against the cap — for this request and every concurrent one — until the returned reservation is settled: recorded as an attempt, or released. So no burst of concurrent requests gets more than max_attempts past the limiter between them. Release in a finally: nothing settles a reservation for you, so one left unsettled holds its slot for the life of the process.

reserve

try_reserve, waiting up to max_wait_ms for a slot when the key is at its cap only because of attempts still in flight.

Each settle (and record and reset) on the key wakes its waiters to re-decide — that key's only, so a settle costs nothing for waiters parked elsewhere: a freed slot is reserved; recorded attempts reaching the cap refuse at once with their real retry_after; reaching max_wait_ms (or signal aborting) refuses with IN_FLIGHT_RETRY_AFTER_SECONDS. At most max_attempts reservations wait on one key — one more is refused at once — so a flood can't park requests without bound. A waiter that leaves, by any path, leaves the key's waiter count as it found it. A waiter holds no place in a queue: each wake, every waiter re-decides, so one can lose every race for a freed slot until max_wait_ms refuses it.

reset

Clear all attempts for key.

Account-grain keys only. Called after a successful auth to forgive a user's own typos, which is safe because the key *is* the account being attacked — clearing it requires that account's credential and can only widen the budget against an account the caller already holds.

Never call this on an IP-aggregate key. That bucket is the distributed-spray backstop, and success on one account must not zero the budget shared by every other account reachable from the same IP; otherwise an attacker interleaves their own logins (or, under open signup, throwaway account creations needing no credential at all) with guesses against arbitrary victims and sprays indefinitely from one address. The only success that records on an IP bucket is an open signup (charged like a failure); no success clears one, so with no reset each is a monotone-within-window counter that only time clears.

Because they are monotone, the IP buckets are one instance per auth surface (login_ip_rate_limiter, signup_ip_rate_limiter, bootstrap_ip_rate_limiter) rather than one shared across all of them. A single instance meant a failure on any surface spent the budget that bounds guessing on every other one, and one caller's exhaustion denied four routes at once — a cost that used to be masked by the reset this doc forbids.

Attempts still in flight on key (reserved by concurrent requests) are kept: a reset forgives what was recorded, not what is still running.

RateLimiterMode
#

rate_limiter.ts view source

RateLimiterMode

type "enforced" | "disabled_for_testing"

import type {RateLimiterMode} from '@fuzdev/fuz_app/rate_limiter.js';

Whether a server builds the rate limiters it is not handed — AppServerOptions.rate_limiters.

  • 'enforced' — every limiter left out of the options is a default instance. The only mode a production server uses, and the default.
  • 'disabled_for_testing' — every limiter left out is null, so nothing is throttled. For in-process test apps and test binaries: they drive many round-trips from one address, and the IP buckets are monotone within their window (a success never refunds them, see RateLimiter.reset), so a suite's failures pile up until every later call is refused.

A limiter passed explicitly — an instance or null — wins over the mode either way, so a rate-limit test enables just the limiter it pins. The disabled mode is loud: create_app_server adds a surface warning, which log_startup_summary logs at assembly, and the first limiter it leaves null prints RATE_LIMITERS_DISABLED_BANNER to stderr once per module instance.

Twin of the Rust spine's fuz_auth::RateLimiterMode (Enforced / DisabledForTesting).

RateLimiterOptions import type {RateLimiterOptions} from '@fuzdev/fuz_app/rate_limiter.js';

Configuration for a rate limiter instance.

max_attempts

Maximum allowed attempts within the window, a safe integer ≥ 0. 0 refuses every attempt — check, try_reserve, and reserve answer at once with the window's length as retry_after, tracking nothing.

type number

window_ms

Sliding window duration in milliseconds, a safe integer ≥ 0.

type number

cleanup_interval_ms

Interval for pruning stale entries, an integer from 0 to PERIODIC_INTERVAL_MS_MAX (0 disables the timer) — the largest delay a timer honours; past it setInterval fires every millisecond.

type number

max_keys?

Maximum tracked keys. When exceeded, the least-recently-used key is evicted — bounds memory under key-enumeration attacks. Default: DEFAULT_RATE_LIMITER_MAX_KEYS (100_000). Pass null to disable the cap (falls back to an unbounded Map — only recommended when the key set is known to be closed, e.g. a per-account limiter keyed to a bounded-size account table).

LRU trade-off: every check / record call marks the key as most-recently-used, so keys under active attack stay fresh and won't be evicted. A slow-burn attacker spread across many low-volume keys can, however, drop out of the table and reset their budget — set max_keys high enough to fit the expected legitimate key set and this stays theoretical.

A number must be a positive safe integer.

type number | null

RateLimitReservation

RateLimitReservation import type {RateLimitReservation} from '@fuzdev/fuz_app/rate_limiter.js';

An attempt admitted by RateLimiter.try_reserve or RateLimiter.reserve, counted against the key's cap until settled.

Settle it exactly once: record keeps it as an attempt (a failure, on the failure-counting surfaces), release gives it back. Both are idempotent and the first call wins, so a handler calls record where the outcome is known and release in a finally. When the key's entry was evicted or reset meanwhile, record still records (into the key's current entry) and release is a no-op. A reservation made against no limiter (try_reserve_optional / reserve_optional with null) is inert.

RESERVATION_WAIT_MAX_MS
#

rate_limiter.ts view source

5000 import {RESERVATION_WAIT_MAX_MS} from '@fuzdev/fuz_app/rate_limiter.js';

How long a password-surface reservation (RateLimiter.reserve) waits for a slot when the key is at its cap only because of attempts still in flight, before answering 429. Mirrors the Rust spine's RESERVATION_WAIT_MAX.

Counting attempts while they are in flight caps *successful* concurrent attempts from one key too — a class behind one NAT logging in together. Those attempts settle within a request's lifetime, so a short wait turns most of those refusals into a late success, while a key at its cap on *recorded* attempts is still refused at once.
