runtime/secure_file.ts

Hardened secret-file read and burn — the TS twins of the Rust spine's fuz_sys::secure_file::load_secure_file and burn_secure_file.

The file this guards is typically the highest-value credential on the host (the bootstrap token mints the keeper account), so the read fails loud rather than degrading: a symlink, a non-regular file (FIFO, device node, directory), a group/other-accessible mode, or an oversized file is refused, never returned — and, for a reader that asks (SecureReadOptions), a file with a link count other than 1. The deploy recipe places the token at 0600, so the check ratifies the shape zap produces; a hand-placed 0644 file fails at boot instead of being read.

The real implementations live here (load_secure_file_node and burn_secure_file_node, wired as create_node_runtime().read_secure_file and .burn_secure_file), and the mock honors the mode/size and link-count checks over its in-memory map (it has no file types). Both refuse through the shared assert_secure_mode / assert_secure_size / assert_secure_link_count helpers, so the checks — and their operator-facing messages — can't drift between them.

burn_secure_file_node
#

runtime/secure_file.ts view source

(path: string): Promise<BurnOutcome> import {burn_secure_file_node} from '@fuzdev/fuz_app/runtime/secure_file.js';

Remove a one-shot secret's directory entry, durably (Node implementation) — the burn a consumed credential file (the bootstrap token) gets before the transaction it authorized commits, so the secret can never be presented again.

  • unlink of the entry at path: a symlink there is removed itself, never followed (following would delete a file the operator never named), and a directory is refused, never recursed into — unlike rm, which takes recursive
  • a missing entry (ENOENT) is 'already_gone', not an error: the postcondition the caller needs — no entry at path — holds
  • then the parent directory is fsynced, on both outcomes, so the removal survives a host crash; without it a crash after the caller's commit can bring the entry back. A failed fsync is a failed burn. Skipped on Windows, which can't open a directory

Twin of the Rust fuz_sys::secure_file::burn_secure_file.

load_secure_file_node
#

runtime/secure_file.ts view source

(path: string, options?: SecureReadOptions | undefined): Promise<Uint8Array<ArrayBufferLike>> import {load_secure_file_node} from '@fuzdev/fuz_app/runtime/secure_file.js';

Read a secret file with fail-loud checks (Node implementation).

  • O_NOFOLLOW atomically rejects symlinks during open (no TOCTOU window)
  • O_NONBLOCK keeps the open from waiting on a FIFO that has no writer (it has no effect on a regular file); the regular-file check on the open descriptor then refuses it, a device node, or a directory
  • O_NOCTTY keeps a terminal device at the path from becoming the process's controlling terminal in the moment before that check refuses it
  • the permission check runs on the open descriptor, not the path, so the file can't be swapped between check and read — any group/other access (not 0600/0400) is refused
  • with require_single_link, a link count other than 1 is refused, read from the same descriptor stat
  • a size cap bounds the read; the read itself is limited to cap + 1 so a file growing between stat and read is still caught

The strictness a secure read adds to its default checks. Default: none. Twin of the Rust fuz_sys::secure_file::SecureReadOptions.

require_single_link?

Refuse a file whose link count is not 1, read from the same descriptor fstat as the other checks. For a one-shot secret its reader burns by unlinking it (the bootstrap token): with a second hard link the unlink leaves the inode, and the secret, readable under the other name. Off by default because a long-lived secret has no such burn, and a snapshot tool that hard-links a key file must not stop the reader.
