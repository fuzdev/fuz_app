http/route_result.ts

What a route handler returns: a success, a failure, or a response it built itself. apply_route_specs turns the result into the Response — a success is its JSON body at 200, a failure its definition's body at the definition's status with the definition's headers (Retry-After), a raw result the response as it is.

A result is plain data, so domain code and shared helpers fail without the Hono context (return route_fail(REST_ROW_NOT_FOUND)), and a handler forwards a failure it was handed (if (!result.ok) return result). Headers and cookies a handler sets on the context before it returns carry over onto the response the framework builds.

Hono-free: hono is imported for its types alone.

A JSON value's type made readonly at every depth: what a handler's route_ok value is checked against. route_ok infers its value as written ({ready: true}, not {ready: boolean}), arrays as readonly tuples, which a readonly array of the output's element type accepts. A tuple reads as an array of its elements. An index signature of unknown (a loose_object's other keys, a record(unknown)) is left out, so a value typed by an interface, which has no index signature, is accepted.

A failure: the route answers {error: def.code, ...fields} at def.status, with the headers def derives from that body.

In a handler it must be one the route allows: a definition in its errors, one its auth or rate_limit derives, or a catch layer's answer (ALWAYS_ACCEPTED_ERRORS) — or any definition whose body one of those accepts at the same status and code.
