http/route_result.ts

What a route handler returns: a success, a failure, a raw answer described as data, or an SSE stream. A handler never builds a Response: apply_route_specs prepares the response from the result inside the route's transaction and builds it only after the commit, through the Hono context (prepare_route_response, emit_route_response in http/route_spec.ts). So every response a route spec answers carries what the middleware put on the context — the session middleware's clear of a stale cookie among it — and a Set-Cookie the handler returns rides only a success whose writes committed.

  • route_ok(value, {set_cookie?}) — value as JSON at 200, the Set-Cookie lines after any the middleware put on the context
  • route_fail(def, fields?) — the definition's body at its status, with the headers it derives (Retry-After); never a cookie
  • route_raw({status, headers?, body?}) — a status, headers, and a body written as given: an empty body, bytes, a stream, a JSON-RPC envelope
  • route_sse(stream) — the stream the route opened for this request (RouteContext.open_sse)

A result is plain data, so domain code and shared helpers fail without the Hono context (return route_fail(REST_ROW_NOT_FOUND)), and a handler — which receives a RouteContext, never the Hono context — forwards a failure it was handed (if (!result.ok) return result).

Hono-free: nothing here imports hono.

route_raw
#

http/route_result.ts view source

(init: RouteRawInit): RouteRaw import {route_raw} from '@fuzdev/fuz_app/http/route_result.js';

A raw answer at any status, described as data: an empty body, bytes, a stream, a JSON-RPC envelope. A JSON answer of the route's own goes through route_ok or route_fail.

The framework checks it when it prepares the response, inside the route's transaction, so a raw answer it refuses throws and rolls back:

  • a status outside 200 to 599
  • a header of ROUTE_RAW_REFUSED_HEADERS, a name or value a Headers refuses, an empty value or an empty list (a runtime writes one its own way), one name twice in any case
  • a non-null body without a Content-Type (a runtime would derive one, each its own way), and a body on a null-body status (204, 205, 304)
  • a Content-Length that is not a decimal integer without a leading zero (0 or [1-9][0-9]*), a list included, one past the safe integer range, one on a 204 or 205 (no content to measure, RFC 9110 §8.6 and §15.3.6; a 304 may name the size of the representation it stands for, §15.4.5), and one a text or bytes body doesn't have — the UTF-8 bytes of a string, the byteLength of a Uint8Array. @hono/node-server sends any of these as written while Bun rewrites them to the body it sends, so the two runtimes would answer differently. With a null or stream body the size is the route's to declare: an X-Accel-Redirect answer sends one with no body
  • a body that is none of RouteRawBody (a Response included), a stream that is locked, bytes whose buffer is detached, and bytes whose resizable buffer shrank below the view — read as empty, they would answer as zero bytes on every runtime

A stream that was read and released is unlocked yet can't be answered with, and nothing shows it before a Response is built from it: that fails after the commit, answering the error catch's 500 with an error naming the route (or, on @hono/node-server, whose own Response reads the stream only as it writes, an empty body). A view whose resizable buffer shrinks after the result is prepared is past what the prepare can see.

A stream body's cancel must release its source — close the file, end the child process: it is the one hook the spine calls for a stream it does not send. A stream body the route does not end up answering with — refused here, or rolled back by a failed commit — is cancelled, and so is one answering a HEAD, which gets the status and headers alone. A source opened before the status is known (a file opened to choose 200 or 404) is released the same way whichever answer it ends up behind.
