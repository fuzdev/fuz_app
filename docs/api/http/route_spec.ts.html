http/route_spec.ts

Introspectable route spec system for Hono apps.

Routes are defined as data (method, path, auth, input/output schemas, handler), then applied to Hono. The attack surface is generated from the specs — always accurate, always complete. A handler returns a result (http/route_result.ts) and apply_route_specs builds the response; a spec is made by define_route (or define_route_shape + attach_route_handler), which checks the handler's results against the route.

Input/output schemas align with SAES ActionSpec conventions, and each is a @fuzdev/fuz_schema schema (AnySchema):

  • input: the request body schema (literal(null) for no body)
  • output: the success response body schema
  • a strict object for inputs (reject unknown keys): object

(app: Hono<BlankEnv, BlankSchema, "/">, specs: RouteSpec[], resolve_auth_guards: AuthGuardResolver, log: Logger, db: Db, options?: ApplyRouteSpecsOptions | undefined): void import {apply_route_specs} from '@fuzdev/fuz_app/http/route_spec.js';

Apply route specs to a Hono app.

For each spec: resolves auth to guards via the provided resolver, adds input validation middleware (for routes with non-null input schemas), runs the optional authorization phase to resolve the acting actor + build the request context, wraps handler with DEV-only output validation, builds each response from its handler's result (prepare_route_response inside the transaction, emit_route_response after it), wraps with error catch layer (a thrown JSON-RPC error, recognized via to_thrown_jsonrpc_error, maps to its status; any other throw to a 500), and registers the route.

Per-route middleware order: content type (415, POST only) → params → query → pre-authorization auth guards (401 + rule-3 scope) → authorization phase → post-authorization auth guards (403) → input validation (400) → handler. The content type goes first because it says almost nothing about the route, and a forged request should be refused before any credential is read. Body validation runs behind every authority gate, so a caller any of them refuse never sees route-shape information from a parse failure — a 400 there would confirm the route exists and describe how to call it. Params and query still validate first (they address the route rather than carry its payload, and the authorization phase reads acting off the query on GETs).

Each handler receives a RouteContext and nothing else: built from the Hono context once every stage before the handler has run, with db transaction-scoped when RouteSpec.transaction is true and the pool otherwise, and open_sse opening through options.open_sse.

A route's response_headers are written on the context by its first stage, ahead of the content-type check, so every answer the route gives carries them; a record off their rules throws at registration.

Also enforces the auth shape's registry-time invariants: the cross-axis invariants 1, 3, and 4 (assert_route_auth_invariants), and invariant 2: auth.actor !== 'none' ⟺ input or query declares acting?: ActingActor. REST is bi-located (GETs declare acting on query, mutations on input), so the check passes both slots; the action-dispatcher registries (compile_action_registry) share the same helper with input only — ActionSpec has no query shape.

Every schema slot (params, query, input, output) must hold a @fuzdev/fuz_schema schema (assert_validation_schema), and every errors entry an error definition (rest_error): anything else throws naming the route and the slot. A params or query must be an object schema (get_schema_entries), as the path params and query string are an object: one that isn't throws naming the route. A GET carries no body, so its input must be a null schema (is_null_schema): any other throws naming the route.

In DEV each handler's 2xx JSON responses are checked against its output. Error responses are checked by the DEV error check (create_dev_route_error_check), which create_app_server mounts outermost.

Two-phase auth guard set returned by AuthGuardResolver.

pre_authorization runs before the authorization phase — the 401 check and the rule-3 token-scope refusal live here, so a caller either one turns away never reaches the actor resolution or the route's body. post_authorization runs after the authorization phase has populated RequestContext — credential / role checks live here because they read c.var.request_context.role_grants.

Both phases run ahead of body validation, which is why neither is named for it: route-shape information stays behind every authority gate. The names say which side of the authorization phase a guard sits on, the only axis that still distinguishes them.

emit_route_response
#

http/route_spec.ts view source

(c: Context<any, any, {}>, prepared: PreparedRouteResponse): Response import {emit_route_response} from '@fuzdev/fuz_app/http/route_spec.js';

Build the response prepare_route_response prepared — the one place a route result becomes a Response, and only once the route's transaction has committed, so nothing a handler returned reaches the wire for writes that rolled back. Built through the Hono context (c.body), so the headers the middleware put on the context — the session middleware's clear of a stale cookie — lead, and a success's Set-Cookie lines follow them in order. A success is written as c.json writes it, a failure as c.json(body, status, headers) does, and an SSE stream with SSE_RESPONSE_HEADERS.

The prepare checked everything it can see. What it can't — a stream body read and released, unlocked yet disturbed — makes the Response constructor throw here, after the commit; apply_route_specs rethrows that as an error naming the route and the commit, which the error catch logs and answers 500.

A HEAD request — which Hono answers by running the GET route and dropping the body unread, never cancelling it — gets a stream's status and headers alone, and the stream released here: an SSE stream is closed, so its on_close listeners run and a registry drops it, and a raw stream body is cancelled, which releases its source (route_raw). An SSE answer to a HEAD leaves out SSE_RESPONSE_HEADERS' Connection: keep-alive, which keeps a stream's connection open and would hold one with no stream on it past a client's Connection: close (@hono/node-server honors it). Text and bytes are built as for a GET — Hono drops them, and an outer layer that reads the answer (the DEV error check) still sees its body.

(result: RouteResult, options: { label: string; opened_sse: ReadonlyMap<SseStream<never>, ReadableStream<Uint8Array<ArrayBufferLike>>>; response_header_names?: ReadonlySet<...> | undefined; close_requested?: boolean | undefined; }): PreparedRouteResponse import {prepare_route_response} from '@fuzdev/fuz_app/http/route_spec.js';

Prepare the response for a handler's result, checking everything it can see that would keep it from being built or framed as declared, so emit_route_response fails only on a stream disturbed past what a check can see (route_raw). Runs inside the route's transaction: a result it refuses throws, the transaction rolls back, and the post-commit effects are discarded. Serializes a success's or a failure's JSON body here for the same reason. Writes nothing.

  • a success — value as JSON, its set_cookie lines kept for the emit
  • a failure — its body as JSON at its status, with the headers its definition derives (Retry-After); a failure carrying set_cookie is refused, since a refusal never sets a cookie
  • a raw answer — checked by the rules route_raw lists
  • an SSE answer — its stream must be one RouteContext.open_sse opened for this request (opened_sse), and the route may not have asked to close the connection (SSE_RESPONSE_HEADERS keep it alive)

A raw or failure result whose headers name one of the route's response_headers, or an SSE answer on a route declaring one of SSE_RESPONSE_HEADERS, is refused: the declared header is the route's on every answer.

RouteContext
#

http/route_spec.ts view source

RouteContext<TAuth, TInput, TParams, TQuery> import type {RouteContext} from '@fuzdev/fuz_app/http/route_spec.js';

Everything a route handler receives: the request as the pipeline resolved and validated it, the per-request deps, and the few effects a handler may ask of the response. A handler takes nothing else — never the Hono context — and returns a result (http/route_result.ts), so nothing it does can write on the response the spine builds after the commit.

The fields it shares with ActionContext (auth, client_ip, signal, db, pending_effects, post_commit_effects) carry the same names and types there, so a helper typed against one of the narrow slices (QueryDeps, EmitAfterCommitContext, AuditEmitterContext) takes either.

Audit writes run through AppDeps.audit.emit(route, input) (see auth/audit_emitter.ts). It writes a success row in the route's transaction when one is open and a failure row on the pool it closes over, so a refused attempt's row survives the rollback.

Routes whose body manages its own transaction (signup, bootstrap) declare transaction: false on the spec, which makes route.db the pool — they reach for it directly.

The route answers JSON-RPC 2.0 envelopes, its refusals included, not REST bodies — the pair create_rpc_endpoint builds. raw_body?

Marks a route whose request and/or response carries raw bytes or a streaming protocol rather than JSON — git smart-HTTP, file-store binary uploads/downloads, raw internal callbacks. Disambiguates the overloaded input: literal(null), which otherwise can't distinguish "no body" (GET /health) from "raw bytes" (a binary upload).

A raw_body POST takes any Content-Type a browser can't send cross-origin without a preflight; every other POST route requires application/json, bodyless or not (415 unsupported_content_type otherwise — see http/simple_request.ts). The schema-driven round-trip test suite auto-skips raw_body routes (it can neither synthesize a meaningful body nor assert a JSON output shape), so consumers don't hand-maintain a skip_routes entry per binary route. Also surfaces in AppSurfaceRoute so generated docs render "raw" instead of a misleading null body.

type boolean

mints_credential?

Marks a route that issues a credential — a session cookie — while declaring no auth itself: login, signup, bootstrap. A forged cross-site request to one is login CSRF, so it must take the origin check, and assembly refuses it outside the auth middleware's scope, where no origin carve-out can reach (assert_credential_routes_in_auth_scope). A route that reads a credential (auth.account not 'none') is held there without the mark.

type boolean

reads_credential?

Marks a route that reads the resolved credential in its handler while declaring no auth gate — it answers an anonymous caller itself instead of taking the dispatcher's 401 (account status, the cell-scoped fact read, the JSON-RPC endpoint whose dispatcher gates each action). Outside the auth middleware's scope no session or bearer parsing runs and it would see every caller as anonymous, so assembly refuses it there (assert_credential_routes_in_auth_scope), as it does a route whose auth.account is not 'none'.

The handler owns the token-scope rule a gate would otherwise apply: a scope-narrowed API token reaches no non-RPC surface that reads account data, and auth.required_scope is refused on a route that admits anonymous callers. Read the credential through get_public_account_id (auth/request_context.ts), not get_resolved_auth, so a narrowed token is answered as the anonymous caller. The RPC endpoint is the exception — its dispatcher gates each method against the scope.

type boolean

response_headers?

Headers every answer of the route carries, once a request reaches it: its own validation and gate refusals, the handler's result of any kind, and the error catch's 500 or 503 (a refusal by middleware ahead of the route, such as the origin check, carries none). For a header true of every answer — Cache-Control: no-store on a per-caller read — not one of a success alone, which the result carries.

One value per name, a name once in any case, a value a Headers accepts and not empty; none of ROUTE_RAW_REFUSED_HEADERS, and neither Content-Type nor Content-Length, which belong to a body. A result whose own headers name one of these is refused when it is prepared — the declared value is the route's for every answer, so a second one is a conflict, not an override. apply_route_specs throws naming the route on a record off these rules.

type Readonly<Record<string, string>>

transaction?

Whether to wrap the handler in a database transaction.

When omitted, defaults are derived from the HTTP method:

  • GET → false (read-only, no transaction)
  • All others (POST, PUT, DELETE, PATCH) → true

Set explicitly to override the default (e.g., false for a POST that manages its own transaction like signup).

type boolean

open_sse

Open the SSE stream this request answers with (route_sse(stream)). The stream exists — send, close, and on_close work — from the moment this returns, so the handler can register it before it answers. Nothing is written on the context: the response is built only when the route answers with the stream, after any commit, through the context (so it carries what the middleware put there) and with SSE_RESPONSE_HEADERS. A stream the handler opens and does not answer with — it answers something else, or throws — is closed and its body cancelled, and the answer carries none of the stream's headers.
