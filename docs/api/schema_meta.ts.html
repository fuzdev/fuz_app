The error.data.reason an input validation failure at path carries: the invalid_reason of the deepest field along path that declares one.

Walks object fields only, each through its wrappers: a segment that is not a key of an object schema (an array index, a union member's key, an unknown key) ends the walk, so a fault inside a declared field still resolves to that field's reason. An empty path — a whole-input fault such as an unrecognized key on the input object — resolves to none, as does a schema that is not an object.

The error.data.reason a failed input parse answers: the declared reason of the first issue's field (resolve_invalid_reason), or none when any issue sits on the input itself. Such an issue is an unknown key on the input object (or a non-object input), which the Rust twin refuses before reading any field, so a stale client sending an extra key gets the same answer from both spines whatever else its body gets wrong.

empty_input_handler_guarded?

Set on an action's input schema that accepts {} by design while its handler refuses {} with a declared reason — an input taking one of several optional selectors, where the handler names the missing or conflicting one (a schema-level refine would answer a reason-less invalid_params first). A call with no input is never valid for such an action, so the typed surface keeps its input required (action_input_is_optional), and the input-shape invariant ("an input accepting {} accepts undefined too") exempts it. Read from the input schema itself, so a wrapper (.optional(), .extend()) drops it.

type boolean

invalid_reason?

The error.data.reason an action input refuses this field with. On a field of an action's input schema, every invalid_params whose first Zod issue lands on the field — missing, wrong type, null, out of range, malformed, or a fault anywhere inside it — carries this reason, where an undeclared field's refusal carries none. The message stays the generic invalid params. A body with faults on several fields answers the first issue's reason in Zod's order, which a twin checking in another order need not match, so the reason is defined for a single-fault body only — except that an issue on the input itself (an unknown key) anywhere among the issues means no reason, as the Rust twin refuses unknown keys first. Declared reasons are named <field>_invalid.

The declaration is the one source of the reason: the dispatcher reads it (perform_action), the adversarial suites expect it, and the Rust twin owes the same reason on every refusal of the field. Read through the field's optional, nullable, default, prefault, transform and pipe layers (not .readonly(), .catch() or z.lazy()), so it may sit on any of them; a declaration on a nested field overrides its parent's for a fault inside it, and an object-level refine whose issue names the field takes its reason too. See resolve_issues_invalid_reason.

type string
